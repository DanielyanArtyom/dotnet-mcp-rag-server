### What will break in a container (current code, unchanged)
1. **No schema, no users.** Migrate and seed are Development-only (`ApplicationBuilderExtension.cs:7`). With `ASPNETCORE_ENVIRONMENT=Production` the first DB query fails (relation does not exist).
2. **No connection string and no JWT secret** in Production config. Startup dies in `AddAuthentication` (null secret), or at the first DB use (null connection string).
3. **NLog file target under `/app/Logs`.** In chiseled images the process runs as UID 1654 and `/app` (copied in by the Dockerfile) is not writable by that user (dotnet-docker distroless doc, §2.8). With `throwExceptions=false`, NLog should drop the file writes silently while console keeps working. That is wasted work and a confusing `Logs/` expectation (inference, not run).
4. **Raw-file storage `/app/App_Data/Documents`** is not writable by UID 1654 and is lost when the container is recreated. Uploads will fail with `UnauthorizedAccessException` until a writable volume is mounted (§2.8).
5. **Port.** The container listens on 8080 (`ASPNETCORE_HTTP_PORTS=8080` set by the base image), not 5119. Compose must map `5119:8080` to keep `lumen-token.sh` and the eval harness working (judgement).
6. **`AllowedHosts: "*"`** works, but the goal is to set it per environment. Pitfall: once it's restricted, any in-container probe that sends `Host: 127.0.0.1` or a container name gets 400 from host filtering. Requests from the host go to `localhost:5119`, so the Host header is `localhost`.
7. **`Mcp:AllowedOrigins` is empty** in Production. Claude Code CLI works (it sends no Origin, per the Stage 5 findings), but MCP Inspector's proxy origin `http://localhost:6274` would get 403 unless it's set through env.
8. **No `/health`.** The chiseled image has no curl or shell, so a Docker `HEALTHCHECK` needs a different mechanism (§2.2).
9. **Swagger is off outside Development** (`Program.cs:18`). "Open Swagger after compose up" won't work unless the compose environment is Development or Swagger gets its own flag (judgement; a decision point).
10. **Seeded placeholder documents** reference raw files that don't exist and carry no `IngestProfile`. Harmless for the API: `File.Delete` on a missing file is a no-op. Possibly noisy for the eval harness corpus check; not verified.

## 2. Research findings

### 2.1 .NET 10 container images and Dockerfile pattern

**Image flavours (aspnet repo).** `mcr.microsoft.com/dotnet/aspnet:10.0` (Debian/Ubuntu "full", includes ICU + tzdata), `aspnet:10.0-noble-chiseled` (Ubuntu 24.04 distroless: "Minimal set of packages … Non-root user by default, No package manager, No shell"), and `aspnet:10.0-noble-chiseled-extra` (chiseled + `icu` + `tzdata`). Source: https://github.com/dotnet/dotnet-docker/blob/main/documentation/ubuntu-chiseled.md, https://github.com/dotnet/dotnet-docker/blob/main/documentation/image-variants.md. There is no chiseled SDK image; build on the full SDK image (same docs). The repo's `main` samples have already moved to .NET 11 (`sdk:11.0-resolute`, `aspnet:11.0-resolute-chiseled`). For .NET 10 the featured chiseled tag is `10.0-noble-chiseled`.

**Compressed sizes** (minimal API, Nov 2025 snapshot), from https://github.com/dotnet/dotnet-docker/blob/main/documentation/sample-image-size-report.md:

| Base | Compressed |
|---|---|
| `aspnet:10.0` | 92.48 MB |
| `aspnet:10.0-noble-chiseled` | 52.81 MB |
| `aspnet:10.0-noble-chiseled-extra` | 67.68 MB |
| `aspnet:10.0-alpine` | 51.93 MB |

**Non-root user and port.** The .NET 10 chiseled runtime-deps Dockerfile sets `APP_UID=1654`, `ASPNETCORE_HTTP_PORTS=8080`, `DOTNET_RUNNING_IN_CONTAINER=true` and `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=true`, and ends with `USER $APP_UID` (https://github.com/dotnet/dotnet-docker/blob/main/src/runtime-deps/10.0/noble-chiseled/amd64/Dockerfile). The full `noble` image also creates user `app` with UID 1654 but does **not** switch to it; it stays root unless you add `USER $APP_UID`. Background: the default port moved from 80 to 8080 "because of the need to provide a good usability experience when switching to a non-root user" (https://learn.microsoft.com/dotnet/core/compatibility/containers/8.0/aspnet-port); the `app` user is described at https://learn.microsoft.com/dotnet/core/compatibility/containers/8.0/app-user.

**Multi-arch.** The `pgvector/pgvector:pg17` and dotnet images are published for amd64 and arm64. Docker Hub API, checked today: `pg17`, `0.8.7-pg17`, `pg17-bookworm`, `pg17-trixie`, all amd64 + arm64.

**Recommended Dockerfile shape** (dotnet-docker samples):
- Cross-build pattern from `samples/AspNetCoreRazorApp/Dockerfile.chiseled`: `FROM --platform=$BUILDPLATFORM mcr.microsoft.com/dotnet/sdk:… AS build`, `ARG TARGETARCH`, `COPY --link <proj>/*.csproj .`, `RUN dotnet restore -a $TARGETARCH`, copy the source, `RUN dotnet publish -a $TARGETARCH --no-restore -o /app`; final stage `FROM aspnet:…-chiseled`, `EXPOSE 8080`, `COPY --link --from=build /app .`, exec-form `ENTRYPOINT`. The SDK runs natively on the build machine and only the RID changes, so there is no QEMU emulation for the build itself.
- Multi-project restore caching from `samples/MultiProjectApp/Dockerfile`: copy each `*.csproj` into its own folder (plus `Directory.Build.props`/`NuGet.config` if present), then restore the entry project, then copy the sources. For Lumen that means copying `src/Lumen.{Domain,Application,Infrastructure,Api}/*.csproj` and then `dotnet restore -a $TARGETARCH src/Lumen.Api/Lumen.Api.csproj`.
- Distroless rule: use exec-form `ENTRYPOINT ["dotnet","Lumen.Api.dll"]` or the apphost `["./Lumen.Api"]`. Shell form fails with "stat /bin/sh: no such file or directory" (https://github.com/dotnet/dotnet-docker/blob/main/documentation/distroless.md). `UseAppHost=false` + `dotnet Lumen.Api.dll` is a common, smaller variant. The official sample keeps the apphost, which `-a $TARGETARCH` builds for the right architecture.
- `.dockerignore` from the sample: `**/bin/`, `**/obj/`, `**/out/`, `Dockerfile*`, `**/*.md`. For Lumen also exclude: `.git`, `.research/`, `.superpowers/`, `**/App_Data/`, `**/Logs/`, `tests/`, `tools/`, `.env`, `.vs/.vscode/.idea`, `**/appsettings.Local.json` (judgement).

**Is invariant globalization safe for Lumen?** In chiseled (non-extra) images the base image forces invariant mode. dotnet-docker warns that `Microsoft.Data.SqlClient` needs ICU (https://github.com/dotnet/dotnet-docker/blob/main/samples/enable-globalization.md); that does not apply here because Lumen uses Npgsql. The code review in §1 found no culture-dependent parsing or formatting that matters: dates are invariant, casing is invariant, digits are ASCII. One remaining risk: in invariant mode, linguistic string operations become ordinal, so ICU's "ignore zero-width characters" behaviour in `IndexOf`/`StartsWith` disappears. That could matter only inside third-party code (SemanticKernel `TextChunker`, AngleSharp, PdfPig). **Not verified.** Cheapest proof: run the Apple 10-K characterization test with `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1` and compare the chunk count, or set `<InvariantGlobalization>true</InvariantGlobalization>` in `Lumen.Api.csproj` so dev, tests and container all behave the same (judgement). Fallback: the `-extra` image (+15 MB).

### 2.2 Health checks in a shell-less image
- Microsoft's own health-check page shows `HEALTHCHECK CMD curl --fail http://localhost:5000/healthz || exit 1`, then notes "`curl` isn't included in the .NET Linux container images" (https://learn.microsoft.com/aspnet/core/host-and-deploy/health-checks). This is true even for the full Debian/Ubuntu aspnet images.
- dotnet-docker issue #4300 "Consider defining a helper 'health check' utility for distroless scenarios" is **still open**. Maintainers: "Not needed for Kubernetes. This is a docker compose need" (richlander); "discussion on this as part of .NET 10 planning. Nothing is decided yet" (mthalman, Dec 2024). The SDK container tooling deliberately doesn't support `HEALTHCHECK` because OCI images ignore it (baronfel). The suggested workaround is a tiny .NET program used as the `HEALTHCHECK` executable (https://github.com/dotnet/dotnet-docker/issues/4300, docs request #4323 closed as a duplicate). Community images exist (`ghcr.io/alexaka1/distroless-dotnet-healthchecks`, NuGet `Docker.HealthCheck`). They are third-party.
- Options for compose:
  - (a) Healthcheck on **postgres only** + API `depends_on: postgres: condition: service_healthy`. API health is checked from the host (`curl localhost:5119/health/ready`). Simplest; no extra binary.
  - (b) An **app subcommand**: Program.cs short-circuits on `args[0] == "healthcheck"`, does `HttpClient.GetAsync("http://localhost:8080/health/live")` and returns 0 or 1, used as `HEALTHCHECK CMD ["dotnet","Lumen.Api.dll","healthcheck"]` or a compose `healthcheck.test` in exec form. Cost: a second `dotnet` process every interval (~tens of MB RSS briefly), plus a little code in Program.cs.
  - (c) A separate tiny console project or a third-party image layer.
  - (d) The full `aspnet:10.0` image + `apt-get install curl`: +40 MB and a bigger attack surface, which defeats the point of chiseled.

### 2.3 ASP.NET Core health checks
- `builder.Services.AddHealthChecks()` + `app.MapHealthChecks(path, new HealthCheckOptions { Predicate = … })`. Liveness vs readiness via tags: `/healthz/live` with `Predicate = _ => false` ("excludes all checks and reports a Healthy status for all calls"); `/healthz/ready` with `Predicate = c => c.Tags.Contains("ready")` (https://learn.microsoft.com/aspnet/core/host-and-deploy/health-checks). `AddHealthChecks` comes from the ASP.NET Core shared framework, so no package is needed.
- Default response: plaintext `Healthy`/`Degraded`/`Unhealthy`. Status codes: Healthy → 200, Degraded → 200, Unhealthy → 503 (same page).
- **DB check, option 1:** `AddDbContextCheck<AppDbContext>(tags: ["ready"])` from `Microsoft.Extensions.Diagnostics.HealthChecks.EntityFrameworkCore`. Latest for .NET 10 is **10.0.12**, which depends on `Microsoft.EntityFrameworkCore.Relational 10.0.12`, the same version Lumen uses (NuGet). "By default, the DbContextHealthCheck calls EF Core's CanConnectAsync". It's maintained by Microsoft and needs no connection string duplication. It uses the scoped `AppDbContext`, which is fine because the tenant query filter doesn't affect `CanConnectAsync`.
- **DB check, option 2:** Xabaril `AspNetCore.HealthChecks.NpgSql` runs `SELECT 1`. Latest **9.0.0 (2024-12-19)**, targets net8.0/netstandard2.0, depends on Npgsql ≥ 8.0.3. "Microsoft doesn't maintain or support AspNetCore.Diagnostics.HealthChecks" (Learn). That adds a third-party dependency for no gain here.
- Auth: `MapHealthChecks` endpoints aren't protected unless `.RequireAuthorization()` is called. Lumen has no fallback authorization policy (`AddAuthorization()` with no `FallbackPolicy`, `WebApplicationBuilderExtensions.cs:94`), so a mapped health endpoint is anonymous by default. App Service requires an anonymous health path when you use your own auth (§2.9). Learn warns that `RequireHost` relies on the spoofable Host header.
- Placement: map health **before** `TenantResolutionMiddleware` matters only if that middleware rejects anonymous requests. It reads the claim only when present (`TenantResolutionMiddleware.cs:16-17`), so it should pass through. Not verified by test.

### 2.4 EF Core migrations in production
From https://learn.microsoft.com/ef/core/managing-schemas/migrations/applying (updated 2026-08):
- Strategy table: SQL script (DBA review, **no** EF locking), **migration bundle** ("For automated deployment, use a migration bundle"; uses locking and seeding), EF CLI (dev), **runtime migration** ("Applications that accept startup migration tradeoffs"; uses locking and seeding).
- "EF Core 9 and later protect migration execution with a database-wide lock, so this can be acceptable for applications that prefer simple deployment … A separate migration deployment step is still preferred when review, least-privilege credentials, coordinated rollout, or high availability is important." Remaining listed risks: the app needs schema-change rights; other app instances may access the DB mid-migration; no easy rollback; SQL is not reviewed.
- Containers: "Generate the bundle during the build and run it as a one-shot deployment job after the database is healthy. Don't install the SDK or run `dotnet ef` in the application image, and don't make every application replica run migrations from its entrypoint." Compose supports this with `depends_on: condition: service_completed_successfully`.
- The lock "is held for the duration of the migration execution, including any seeding code" (`UseSeeding`/`UseAsyncSeeding`). EF 9+ `Migrate()` throws on pending model changes (`PendingModelChangesWarning`). Wrapping `MigrateAsync` in an explicit transaction is not supported.
- **Npgsql's lock implementation** (provider source, https://github.com/npgsql/efcore.pg/blob/main/src/EFCore.PG/Migrations/Internal/NpgsqlHistoryRepository.cs): `LOCK TABLE "__EFMigrationsHistory" IN ACCESS EXCLUSIVE MODE` with `LockReleaseBehavior.Transaction`. The lock is tied to the transaction, so it's released on commit, rollback or a dropped connection, and nothing is left stuck after a crash (unlike SQLite's `__EFMigrationsLock` table). The repository also handles the "CREATE TABLE IF NOT EXISTS isn't concurrency-safe" race when it creates the history table. **So two replicas calling `MigrateAsync` at startup are serialized on Postgres**, which matters for the deferred 2-replica test.
- Bundle mechanics: `dotnet ef migrations bundle --self-contained -r linux-x64|linux-arm64 -o efbundle`; run as `./efbundle --connection "$CONN"`. Set `ASPNETCORE_ENVIRONMENT=Production` when building and running it so it doesn't pick up dev user-secrets. A bundle needs `dotnet-ef` in the build stage and a separate runtime image. A chiseled image has no shell, so the bundle container would use `runtime-deps:10.0-noble-chiseled` with an exec-form entrypoint. That is more Dockerfile and a second compose service.

### 2.5 Configuration through environment variables
- "All platforms support the double underscore (`__`) syntax and automatically replace it with a colon (`:`)". Environment variables override `appsettings.json`, `appsettings.{ENV}.json` and user secrets. User secrets load only in Development (https://learn.microsoft.com/aspnet/core/fundamentals/configuration/). Arrays bind by index: `Mcp__AllowedOrigins__0=http://localhost:6274`. Env vars **merge** with JSON by index rather than replacing the array; harmless here because the base `appsettings.json` has `[]`.
- Compose interpolation: `${VAR:-default}` (default if unset or empty), `${VAR:?err}` (**error if unset or empty**), `${VAR?err}` (error if unset). The `.env` file sits next to the compose file. Precedence: shell env > `--env-file` > `.env`. `.env` values feed interpolation only; they reach the container only through `environment:` (or `env_file:`) (https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/).
- Fail-fast in the app: `AddOptions<JwtOptions>().Bind(...).Validate(o => Encoding.UTF8.GetByteCount(o.Secret ?? "") >= 32, "...").ValidateOnStart()` would match the existing pattern. But `AddAuthentication` reads the section eagerly before options validation runs (`WebApplicationBuilderExtensions.cs:76`), so either move the key construction behind `IOptions`/`IConfigureNamedOptions<JwtBearerOptions>` or guard there explicitly (judgement).
- Host filtering: `AllowedHosts` is a semicolon-separated host list without ports (ASP.NET Core host filtering middleware). Set `AllowedHosts=localhost;127.0.0.1` for compose. Docker's `.env` should hold `JWT_SECRET`, `POSTGRES_PASSWORD`, and Azure keys if used.

### 2.6 Postgres in compose
- The Docker docs startup-order example: `depends_on: db: condition: service_healthy, restart: true`, and a db healthcheck `test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]`. Conditions: `service_started` | `service_healthy` | `service_completed_successfully` (https://docs.docker.com/compose/how-tos/startup-order/). `$$` escapes interpolation so the variable is expanded inside the container. The pgvector image is Debian-based and has a shell and `pg_isready`.
- Keep the named volume. For pg17, the data path `/var/lib/postgresql/data` stays as it is today.
- Local pgvector 0.8.7 vs Azure Flexible Server 0.8.2 (§2.9): Lumen uses only `vector(1536)`, `<=>` and exact scan, which are fine on both.
- Publishing 5432 to the host is optional in the all-in-compose setup. Keeping it lets `dotnet run` and the tests share the DB (judgement).

### 2.7 NLog in containers
- NLog 5+ automatically reads an `"NLog"` section from `appsettings*.json` when `UseNLog()`/`AddNLog()` is used, so `appsettings.Production.json` can override targets and rules, and env vars can override too (https://github.com/NLog/NLog.Extensions.Logging/wiki/NLog-configuration-with-appsettings.json). The precedence between `nlog.config` and the appsettings section isn't stated on that page.
- Documented environment-specific options (https://github.com/NLog/NLog/wiki/Environment-specific-NLog-Logging-Configuration): `<include file="nlog_${environment:DOTNET_ENVIRONMENT}.config" ignoreErrors="true" />`, or `LoadConfigurationFromAppSettings()` (recommended for NLog.Web; it also looks for `nlog.{environment}.config`). Whether plain `UseNLog()` auto-loads `nlog.{env}.config` is **not documented/verified**.
- Container practice is stdout only, so `docker logs` and App Service log stream pick it up. The file target is redundant in a container and can't write to `/app/Logs` as UID 1654 (§2.8).
- Simplest switch that keeps one file **(judgement)**: write the file rule as `<logger name="*" minlevel="${configsetting:item=Logging.FileMinLevel:whenEmpty=Info}" writeTo="file" />`, or gate it with an env var via `${environment:…}`, and set it to `Off` in the container. Alternative: drop the file target when `DOTNET_RUNNING_IN_CONTAINER=true`. The console layout already includes exceptions; JSON console layout is optional.

### 2.8 Writable storage for a non-root user
- dotnet-docker distroless doc: the app gets `System.UnauthorizedAccessException` when writing where it has no rights; "By design, an app shouldn't be able to modify the directory it's running from. Instead, you should try to write to the non-root user's home directory"; for bind or volume mounts "make sure the directory gives the correct permissions to the non-root user"; the UID is in `APP_UID` (1654) (https://github.com/dotnet/dotnet-docker/blob/main/documentation/distroless.md).
- Docker named volumes: when a **new, empty** named volume is mounted over a directory that exists in the image, "Docker copies the directory's contents into the volume" (https://docs.docker.com/engine/storage/volumes/). The docs don't state ownership. In practice the directory's owner and mode are copied too, which is why the usual fix works; not verified on the current Docker version. The fix for a shell-less final image: create the directory in the build stage and copy it with ownership, e.g. `RUN mkdir -p /out/data/documents` in the SDK stage, then `COPY --from=build --chown=$APP_UID:$APP_UID /out/data /data`, and set `DocumentStorage__RootPath=/data/documents` and the volume at `/data`. Bind mounts don't get this treatment; the host directory must be writable by UID 1654.
- Alternative: point `DocumentStorage__RootPath` under `/home/app` (owned by 1654 in chiseled: `COPY --chown=$APP_UID:$APP_UID /rootfs/home/app /home/app` in the base Dockerfile) and mount the volume there.

### 2.9 Brief: Azure App Service (Linux container), for a "How I'd deploy" section
- **Port:** App Service needs to know the container port: set `WEBSITES_PORT=8080` (from the .NET 8 port breaking-change doc's Azure list).
- **Health check:** you configure a path, and App Service pings every instance once a minute. If an instance doesn't answer 200-299 after 10 requests (`WEBSITE_HEALTHCHECK_MAXPINGFAILURES` 2-10), it's removed from the load balancer and replaced after an hour unhealthy. A ping counts as failed after a 1-minute timeout. Redirects (302/307) count as failures. "If you use your own authentication system, the Health check path must allow anonymous access". The full benefit needs ≥2 instances. The guidance is that the path "should check critical components", e.g. the DB (https://learn.microsoft.com/azure/app-service/monitor-instances-health-check). For Lumen, point it at `/health/ready` (judgement).
- **Managed identity for Azure OpenAI:** already supported. An empty `ApiKey` switches `CreateOpenAIClient` to `BearerTokenPolicy(new DefaultAzureCredential(), "https://ai.azure.com/.default")` (`src/Lumen.Infrastructure/DependencyInjection/ServiceCollectionExtensions.cs:64-76`). It would need a system-assigned identity plus an Azure OpenAI data-plane role (e.g. "Cognitive Services OpenAI User"; role name not re-verified in this pass).
- **Azure Database for PostgreSQL Flexible Server:** allow-list `vector` in the `azure.extensions` server parameter (the name is `vector`, not `pgvector`), check with `SHOW azure.extensions;`, then `CREATE EXTENSION vector` per database (Lumen's migration does this). Supported version is **0.8.2 for PG 13-18** (https://learn.microsoft.com/azure/postgresql/extensions/how-to-use-pgvector, https://learn.microsoft.com/azure/postgresql/extensions/concepts-extensions-versions). Entra auth for Npgsql would need a token-provider data source; not researched.
- **Key Vault references:** an App Setting value `@Microsoft.KeyVault(SecretUri=https://<vault>.vault.azure.net/secrets/<name>)` or `@Microsoft.KeyVault(VaultName=…;SecretName=…)`. It uses the system-assigned identity by default, which needs **Key Vault Secrets User** (RBAC) or Get (access policy). The cache is refreshed every 24 h or on restart. An unresolved reference is passed to the app as the literal string (https://learn.microsoft.com/azure/app-service/app-service-key-vault-references). Use it for `Jwt__Secret` and the connection string.
- **Raw files:** the container filesystem is ephemeral, so replace `LocalFileStorage` with a Blob Storage implementation of `IFileStorage` (Azure.Storage.Blobs + `DefaultAzureCredential`, role "Storage Blob Data Contributor"). The seam already exists. Not researched further.
- **Migrations on Azure:** per §2.4, a bundle as a deploy step is the documented preference. The runtime-migrate flag remains acceptable at 1-2 instances thanks to the Npgsql table lock, but the app's DB user then needs DDL rights.

## 4. Open questions and things not verified
1. Invariant globalization vs SemanticKernel `TextChunker`/AngleSharp/PdfPig: needs one run of the characterization test with invariant mode on.
2. Whether a named volume copies the owner/mode of the image directory on first mount. The Docker docs say contents are copied but don't mention ownership; verify with one `docker compose up`.
3. NLog behaviour when the file target can't create `/app/Logs` (expected: silently dropped with `throwExceptions=false`), and whether `UseNLog()` auto-loads `nlog.{env}.config`.
4. Short JWT secret: exact failure point (expected IDX10720 at the first token issue, not at startup). Not run.
5. `AllowedHosts` in base `appsettings.json`: keep `*` (dev convenience; compose overrides it) or make it restrictive and require env. Also, does App Service's health ping send a Host header that passes a restrictive list (the default `*.azurewebsites.net` domain)? Not checked.
6. Whether the seeded placeholder documents (no `IngestProfile`, no chunks) trip the eval harness profile check on a fresh compose DB.
7. CREATE EXTENSION rights for a non-superuser app role. Compose uses `postgres` so it's fine; on Azure the admin role can create allow-listed extensions. Not tested.
8. Npgsql type loading after `CREATE EXTENSION vector` in the same process: works today in Development and in the integration tests (fresh DB, migrate, then vector inserts), so no `ReloadTypes()` seems needed. Keep watching it in the container.
9. The Azure OpenAI data-plane role name and Npgsql Entra-token auth were not re-verified (only needed for the optional Azure text).
