# Lumen Stage 1 — progress record

Status: **complete**. All 13 tasks from `plan.md` implemented and reviewed; a follow-up architecture/style pass then revised several structural choices (tracked separately in `.research/specification/csharp-project-conventions.md`) — this file is the narrative of both. Written for permanent reference (interview prep, and so a future stage doesn't have to reconstruct "what actually happened" from scratch). The process ledger this was distilled from lives at `.superpowers/sdd/plan/progress.md` (a working, disposable artifact of the subagent-driven-development process — this file is the durable summary).

## How it was executed

Followed `superpowers:subagent-driven-development`: a fresh implementer subagent per task, a task-scoped reviewer after each (spec compliance + code quality), a fix loop when the reviewer found something, and a final whole-branch review at the end. Model tiers were matched to task complexity (cheap models for mechanical/complete-code-given tasks, mid-tier for multi-file integration work, most capable for the final review). A preflight scan across all 13 tasks' interfaces/dependencies was run before Task 1 to catch cross-task conflicts early.

**Commit policy note:** this repository's `CLAUDE.md` forbids the AI session from ever running `git commit` — the user commits everything by hand. Every task's changes were staged (`git add`) but never committed; task boundaries for diff/review purposes were tracked via `git write-tree` snapshots instead of commit SHAs.

## The 13 tasks (original build)

1. Solution scaffolding — 4-project Onion solution (`Lumen.slnx`, .NET 10) + 2 test projects, dependency direction Domain ← Application ← Infrastructure ← Api, `docker-compose.yml`.
2. Domain layer — `Role`, `Tenant`, `User`, `Document` POCOs.
3. Persistence — `ITenantEntity`, EF entities + configurations, `AppDbContext` with the tenant global query filter and the `SaveChangesAsync` auto-stamp, `PostgresFixture` (Testcontainers). Isolation test written first and confirmed to fail with a runtime "relation does not exist" error (no migration yet) rather than a compile error — the correct intermediate state.
4. EF Core migrations — initial migration; the isolation test from Task 3 turns green.
5. AutoMapper profiles + `DocumentDto`. **Caught mid-task:** the plan's literal `DomainDtoMappingProfile` code used `.ReverseMap()` on `Document ↔ DocumentDto`, which the plan assumed would fail `AssertConfigurationIsValid()` (Document has `TenantId`, the Dto doesn't) — that assumption turned out to be **wrong**, verified empirically later in the session (neither AutoMapper 16.2.0 nor 12.0.1 actually throws for that shape), but the one-way map was kept anyway as the correct call on its own merits (the reverse direction is genuinely dead code — nothing ever calls `mapper.Map<Document>(dto)`). Cost of the wrong initial assumption: one wasted fix round, and a since-reverted downgrade to a vulnerable AutoMapper version that had to be caught and undone before it went anywhere.
6. Repository + UnitOfWork over one shared `AppDbContext` — deliberately correcting a bug pattern from a past project (there, each repository method opened its own `DbContext` via `IDbContextFactory`, so writes never actually persisted). The test that would have caught that exact bug (`DocumentRepositoryTests.Add_then_Complete_actually_persists_the_document`) passed.
7. Custom exceptions + `IExceptionHandler`-based global error handling; first real `Program.cs`.
8. JWT token service — `sub`/`tenant_id`/role claims.
9. Login flow — `UserLookupService.FindByEmailAcrossTenantsAsync`, the *only* legal `.IgnoreQueryFilters()` call site in the codebase; `Program.cs` gains EF/MediatR/AutoMapper/repo registrations.
10. JWT bearer authentication + `TenantResolutionMiddleware`. Expected intermediate state: the isolation-adjacent test that hits `/documents` still 404s (route doesn't exist until Task 11), not 401 — confirms the auth pipeline itself is wired correctly.
11. Document CQRS slice + `DocumentsController` + Swagger JWT support. The Task 10 test turns into a real 401. **Found and fixed in review:** the implementer's unprompted deletion of the now-orphaned `DiagnosticsController` also deleted `GlobalExceptionHandlerTests`, silently dropping coverage for 4 of 5 exception→status mappings (only `UnauthorizedException` had any other coverage). Fixed by adding a focused unit test exercising `GlobalExceptionHandler.TryHandleAsync` directly for all 5 exception types.
12. Idempotent seed data (`DbSeeder`) — two tenants, one Admin user + one Document each. Manual verification (`docker compose up`, Swagger UI, confirm tenant isolation visually) deliberately left to the user per `CLAUDE.md`'s "Working with the user" convention — hands-on verification is the actual interview-prep value, not something to automate away.
13. The flagship isolation test — two tenants, real JWTs from a real `POST /auth/token` call, real HTTP through `WebApplicationFactory`, proving one tenant's document list never contains the other's data. `CLAUDE.md`'s status section and a `DECISIONS.md` entry written once the suite was green.

**Final whole-branch review** (most capable model) found the architecture sound and all six hard global constraints holding, but surfaced 7 Important findings. Two were deliberately **not** included in the automated fix wave, with rulings recorded: a schema-level FK (would have broken two already-reviewed tests that predate it existing) and the tenant-stamp "only if `Guid.Empty`" semantics (no live exploit path existed yet, and the "obvious" fix would have broken the seeder). The other five were fixed in one batch: completed the `SaveChanges` override to cover all four EF Core overloads, added logging + routed error responses through the registered `IProblemDetailsService` in `GlobalExceptionHandler`, added two more assertions to the flagship isolation test (IDOR-by-id, write-path-over-HTTP), added data annotations to `CreateDocumentCommand` (catching, in the same pass, that the brief's literal `[property: ...]` attribute placement would have made MVC's `ValidationVisitor` throw a 500 on every `POST /documents` — fixed by targeting the constructor parameters instead), and pinned an EF Core Relational package version conflict that had the test suite silently running against a different EF build than the app shipped. Result at that point: 23/23 tests (11 unit, 12 integration).

## Post-completion architecture/style pass

After Stage 1's 13 tasks and final review were done, a separate, deliberate pass revised several structural decisions — driven by direct review of the generated code rather than a new brainstorming/planning cycle, since the changes were refinements to already-working code, not new features. Full rationale for each: `.research/specification/csharp-project-conventions.md`. Summary of what changed and why it isn't just churn:

- **DTOs relocated** from `Lumen.Application` into `Lumen.Api/DTO/{Requests,Responses}/` — Application's CQRS handlers now work purely in Domain models, losing their `IMapper` dependency entirely (mapping happens once, in the controller).
- **`Abstractions/` renamed to `Interfaces/`** in `Lumen.Application` — naming preference, applied consistently across every consumer.
- **Primary-constructor DI converted to traditional constructor + readonly fields** across every DI-constructed class in Api, Application, and Infrastructure.
- **`GlobalUsings.cs` introduced per project**, with a 2+-file promotion rule and a fixed 4-block internal grouping (Lumen → Microsoft → System → third-party). Required two separate full audits (a straightforward per-file grep pass, then a more rigorous empty-file-and-read-the-compile-errors pass after the usings had been substantially reshuffled and a simple grep-based check would have missed an over-promoted namespace).
- **`Extensions/`, `DependencyInjection/`, `Constants/` folders introduced**, modeled on a sibling reference project — `Program.cs` reduced to a service-registration call plus a fluent extension-method chain plus the app-pipeline calls.
- **Routes changed to `[Route("api/[controller]")]`** on both controllers (`/api/auth/token`, `/api/documents`).
- **`AppDbContextFactory` removed** after the user questioned its necessity — verified empirically (not just argued) that `dotnet ef` tooling on this .NET version builds the real application host rather than needing a bespoke design-time factory.
- **A real foreign key added** from `Documents.TenantId`/`Users.TenantId` to `Tenants.Id` (previously just an index) — required updating three tests that pre-dated the constraint to seed a real `Tenants` row.
- **Tenant-stamping made unconditional** (`AppDbContext.SaveChanges` always overwrites `TenantId` from the ambient tenant now, not only when it was `Guid.Empty`) — closes a theoretical gap where a future client-supplied `TenantId` field could have overridden the server's own notion of the caller's tenant. `TenantScopedWriter` is the sanctioned way to write on behalf of a specific tenant outside a real request (seeding).
- **Integration test duplication removed** via a new `tests/Lumen.IntegrationTests/Utils/` folder (`TestDbContextFactory`, `TestWebApplicationFactory`, `TestDataSeeder`, `TestAuth`) and `IAsyncLifetime`-based per-test setup/teardown, closing an old deferred "undisposed `WebApplicationFactory`" finding as a side effect.

**One real incident during this pass, worth recording honestly:** partway through, every integration test that goes through `WebApplicationFactory<Program>` started failing with 404s (9 of 12), while the 3 pure-EF-Core tests kept passing — a clean enough pattern to diagnose via a disposable diagnostic test that dumped the actual registered routes. The cause turned out to be `[Route("api/[controller]")]` sitting where `[Route("auth")]`/`[Route("documents")]` used to be — investigated at length (checked every edit command run that session, ruled out stale build artifacts via `dotnet clean`) before the user clarified they'd made that exact edit themselves via the IDE mid-session and simply hadn't mentioned it. The investigation itself was sound; there was just no AI-side root cause to find. Lesson for next time: when something inexplicably changes underfoot, ask early rather than spending a long diagnostic pass — the user may have touched the file directly.
