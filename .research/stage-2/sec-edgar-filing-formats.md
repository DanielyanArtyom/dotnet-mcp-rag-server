# SEC EDGAR filing formats — what a 10-K/10-Q accession actually contains

Sources current as of **2026-09-13**. Every claim is tied to a primary source (sec.gov / data.sec.gov) with the page's own last-updated date where visible; unconfirmed claims are flagged explicitly. Scope: file formats and structure only — chunking strategy and .NET libraries are covered elsewhere.

## Summary

A 10-K/10-Q "filing" on EDGAR is not one file — it's a numbered **accession** (folder) of dozens of files: one primary document (now almost always **inline‑XBRL HTML**, i.e. ordinary HTML with XBRL tags embedded inline), several exhibit HTML files, a full set of raw XBRL taxonomy/linkbase files, an **extracted plain XBRL instance** SEC generates from the inline doc, ~50-100 auto-rendered `R*.htm` fragment files (one per financial-statement note/schedule), and supporting metadata (`FilingSummary.xml`, `MetaLinks.json`, `Financial_Report.xlsx`). Everything is free, public-domain-in-practice, and reachable via well-documented JSON/XBRL REST APIs at `data.sec.gov`, gated only by a required descriptive `User-Agent` header and a **10 requests/second** rate ceiling. Structured financial facts (tagged with `us-gaap:*` concepts) are available independently of parsing the narrative HTML, both embedded in the primary document (as `ix:` tags) and as a separately generated machine-readable XBRL instance/JSON API — this is directly usable as ground truth for anchoring table chunks instead of parsing raw HTML tables.

## 1. What formats does EDGAR actually serve a 10-K/10-Q in?

**HTML (inline XBRL) is the norm today; plain ASCII text and raw XBRL exist as companion/legacy formats; PDF is only ever a secondary "courtesy" copy, never the official primary document for a 10-K/10-Q.**

- EDGAR's accepted submission formats are **HTML, ASCII (plain text), PDF, or XBRL** — but for most form types, including 10-K/10-Q, **a filed PDF is an "Unofficial Document" ("courtesy copy") and must be submitted alongside an HTML or ASCII counterpart**; only a short, specifically enumerated list of exhibit types (e.g. the Form ARS "glossy" annual report, Exhibit 99 on Form 6-K, Exhibit 96 on Form 10-K/20-F) are allowed as an *official* PDF. [EDGAR Filer Manual Volume II (v.5-10, 2026-03-16)](https://www.sec.gov/files/edgar/filermanual/efmvol2-c5.pdf) §5.2.3.6 (per search-indexed excerpt; PDF not paginated-verified line-by-line — see "Uncertain" below).
- EDGAR only accepts documents in **"a subset of HTML 3.2 semantics (tags) and some HTML 4.0 attributes"** — this is the SEC's own filer manual language, corroborated across multiple filer-manual editions found via search (2025 and 2026 editions). Financial statement tables must be real `<TABLE>` markup with rows/columns — **"images of tables are not allowed."** No active content: no `<APPLET>`, `<OBJECT>`, `<SCRIPT>`, and no external references except `<A HREF>` links back to other EDGAR filings.
- **Inline XBRL (iXBRL) has been mandatory** for operating-company 10-K/10-Q filings since a phased rollout under **Release No. 33-10514, adopted 2018-06-28**. Under inline XBRL, the filer produces **one document that is simultaneously the human-readable filing and the machine-readable XBRL-tagged document** — no separate "generate HTML, then separately tag a copy for an XBRL exhibit" step. [SEC — Inline XBRL](https://www.sec.gov/data-research/structured-data/inline-xbrl) (Last Reviewed or Updated: **2025-01-17**).
- A real, current example — Apple's FY2025 10-K, accession `0000320193-25-000079`, filed 2025-10-31 — confirms the shape in practice. Its accession directory (`index.json`) contains, among others:
  - **`aapl-20250927.htm`** — the primary document (inline-XBRL HTML, 1.5 MB)
  - **`0000320193-25-000079.txt`** — the full plain-text/SGML submission (legacy full-text format, still generated for every filing)
  - **`0000320193-25-000079-index.html` / `-index.json` / `-index.xml`** — the filing index in three parallel formats
  - Exhibit HTML files (`a10-kexhibit21109272025.htm`, etc.)
  - Raw XBRL taxonomy files: `aapl-20250927.xsd` (schema), `_cal.xml` (calculation linkbase), `_def.xml` (definition linkbase), `_lab.xml` (label linkbase), `_pre.xml` (presentation linkbase)
  - **`aapl-20250927_htm.xml`** — a plain XBRL **instance document that EDGAR's own dissemination pipeline extracts from the inline-XBRL primary document** (naming convention `<primarydoc>_htm.xml`) — i.e. even though the filer submits only the inline HTML, SEC's system still produces a conventional, non-inline instance file as an output artifact
  - `0000320193-25-000079-xbrl.zip` — all the above XBRL files bundled
  - `FilingSummary.xml`, `MetaLinks.json`, `Financial_Report.xlsx`, `report.css`, `Show.js` — EDGAR-viewer support files (see §2)
  - **70 files `R1.htm` … R70.htm`** — one auto-rendered HTML fragment per statement/note/schedule (see §2)
  - A couple of `_g1.jpg`/`_g2.jpg` chart images
  
  [`https://www.sec.gov/Archives/edgar/data/320193/000032019325000079/index.json`](https://www.sec.gov/Archives/edgar/data/320193/000032019325000079/index.json) (fetched 2026-09-13; timestamps in the listing show all files modified 2025-10-31).

**Accession directory/URL structure**, confirmed from SEC's own accessing-EDGAR-data page:

- Accession number format: `0001193125-15-118890` = 10-digit CIK of the filer's agent + 2-digit year + sequence number ("usually, but not always, reset to zero" each calendar year).
- Canonical document URL: `https://www.sec.gov/Archives/edgar/data/{CIK-no-leading-zeros}/{accession-no-dashes}/{filename}` — e.g. `.../data/320193/000032019325000079/aapl-20250927.htm`.
- Every accession folder auto-exposes three parallel index formats for automated crawling: `index.html`, `index.xml`, **`index.json`** (append to the folder URL) — `index.json`'s `directory.item` array gives every filename, size, and last-modified timestamp, which is the practical way to enumerate an accession's files programmatically rather than scraping the human index page.
- The legacy full submission is also available as one flat file: `/Archives/edgar/data/{CIK}/{accession}.txt` (concatenated SGML/text of the whole submission — still generated even for HTML-era filings) and `{accession}.hdr.sgml` (header only).

[SEC — Accessing EDGAR Data](https://www.sec.gov/search-filings/edgar-search-assistance/accessing-edgar-data) (Last Reviewed or Updated: **2024-06-26**).

## 2. How messy is the HTML really?

Primary-source evidence supports "genuinely messy, by regulatory construction" rather than "messy by filer carelessness":

- The HTML is restricted to an **old, small tag/attribute subset (HTML 3.2 + partial HTML 4.0)** — see §1. This is a real, documented constraint (not an inference): it means filers/financial printers cannot use modern semantic HTML or CSS layout (flexbox/grid) and instead lean on `<table>` for both real tabular data *and* visual layout/alignment, because tables plus manual cell widths are effectively the only positioning primitive the accepted subset gives them. This is the well-known root cause of "layout tables nested inside data tables" in EDGAR HTML filings; it follows directly from the filer manual's tag-subset rule even though the manual doesn't use the word "nested" itself.
- Financial statement tables are **required** to be real `<table>` markup (images of tables are explicitly disallowed) — so financial statement content is at least reliably table-tagged, not rasterized; the mess is in *how* those tables are built (merged cells for multi-column headers, footnote markers as superscript `<sup>` or separate `<font>`-styled spans, currency/parenthetical-negative formatting baked into text rather than a semantic negative-number type), not whether tabular structure exists at all.
- The 70 `R1.htm`…`R70.htm` files in the Apple example are **EDGAR's own auto-generated "Financial Report" rendering** — one HTML fragment per statement/note/schedule, built by SEC's viewer tooling from the XBRL data (`report.css` + `Show.js` are the supporting stylesheet/script for that same viewer; `FilingSummary.xml` is the manifest mapping each `R*.htm` to its statement name/role; `MetaLinks.json` carries per-fact taxonomy metadata; `Financial_Report.xlsx` is a spreadsheet rendering of the same). These `R*.htm` files are **not the filed document** — they're SEC-generated from XBRL — but they are a much cleaner, one-statement-per-file, machine-produced alternative to parsing the same tables out of the primary narrative HTML, and worth strong consideration as an ingestion source for statement/table chunks specifically.
- **Uncertain / could not verify directly against a primary source:** page-break artifacts inherited from print-oriented authoring (e.g. stray `<hr>`/`<div style="page-break-before">`, empty paragraph runs, footer/header text repeated per "page") are extremely commonly reported by practitioners and are a predictable consequence of filings being authored in Word/financial-printer tools designed for print output, but I did not find an SEC-authored document that names this artifact explicitly. Treat as "very likely, confirm empirically against the actual downloaded 10-K/10-Q" rather than a cited fact.
- **Uncertain:** I was not able to fetch/quote the exact HTML-restriction section text of the EDGAR Filer Manual Volume II PDF directly (large binary PDF; only search-engine-indexed excerpts were retrievable in this session) — the "HTML 3.2 subset" and "no images of tables" claims above come from consistent search-result excerpts of that manual (multiple dated editions: 2025-03, 2025-06, 2026-03) rather than a direct page fetch. Worth a direct read of [efmvol2-c5.pdf](https://www.sec.gov/files/edgar/filermanual/efmvol2-c5.pdf) §5 before finalizing HTML-cleaning logic.

## 3. Free, official APIs to fetch filings programmatically

All confirmed from SEC's own API documentation page and cross-checked against `www.sec.gov`'s developer/access policy pages.

| API | Endpoint pattern | Purpose |
|---|---|---|
| **Submissions** | `https://data.sec.gov/submissions/CIK##########.json` (10-digit, zero-padded CIK) | Filer metadata (current/former names, tickers, exchanges) + filing history — "at least one year of filing history or the 1,000 most recent filings, whichever is more" |
| **XBRL Company Concept** | `https://data.sec.gov/api/xbrl/companyconcept/CIK##########/us-gaap/{ConceptName}.json` | All disclosures of one taxonomy concept (e.g. `Revenues`) for one company, across all filings, split into arrays per unit of measure |
| **XBRL Company Facts** | `https://data.sec.gov/api/xbrl/companyfacts/CIK##########.json` | All XBRL concepts for one company in a single call (aggregates Company Concept) |
| **XBRL Frames** | `https://data.sec.gov/api/xbrl/frames/us-gaap/{Concept}/{Unit}/{Period}.json` — period as `CY####` (annual), `CY####Q#` (quarterly), `CY####Q#I` (instantaneous) | One concept/period, across *all* filers — cross-sectional rather than per-company |
| **Full-Text Search** | `https://efts.sec.gov/LATEST/search-index?q=...` (backs the UI at `https://www.sec.gov/edgar/search/`) | Keyword/phrase/boolean search across full filing text, form type, filer, date-range, SIC code, 2001-present |

[SEC — EDGAR Application Programming Interfaces](https://www.sec.gov/search-filings/edgar-application-programming-interfaces) (Last Updated: **2025-04-08**); [SEC — EDGAR Full Text Search FAQ](https://www.sec.gov/edgar/search/efts-faq.html).

Key characteristics, confirmed:

- **No API key / no authentication** for any of the above — they're plain unauthenticated JSON over HTTPS.
- **No CORS support** — a browser can't call these cross-origin; server-side calls only.
- JSON APIs update **"in real-time as submissions disseminate"**: submissions API has a "typical processing delay of less than a second," XBRL APIs "under a minute." Bulk ZIP archives of the same data are regenerated nightly, ~3:00am ET.
- **Rate limit: 10 requests/second maximum**, stated identically across SEC's own policy pages: *"Current guidelines limit each user to a total of no more than 10 requests per second, regardless of the number of machines used to submit requests."* Exceeding it risks a temporary IP block until the rate drops back under the threshold. [SEC.gov — Privacy Information](https://www.sec.gov/about/privacy-information) (Last Updated: **2023-11-29**); corroborated on the developer-facing [SEC.gov Web Site Privacy and Security Policy / Developer FAQ](https://www.sec.gov/os/webmaster-faq) (Last Reviewed or Updated: **2024-08-23**).
- **A descriptive `User-Agent` header is required** on every request, in the form the SEC itself documents as e.g. `User-Agent: Sample Company Name AdminContact@<samplecompanydomain>.com` — i.e. an organization/app name plus a real contact email, not a generic browser UA string. Automated access is explicitly *allowed* ("We allow scripted access to sec.gov content") conditioned on this header and the rate limit — but **"The SEC does not allow 'unclassified' bots or automated tools to crawl the site"** per the privacy-information page, reinforcing that the declared User-Agent must be genuinely identifying.
- Practical implication for a .NET ingestion service: set a fixed, descriptive `User-Agent` (app name + a real contact email — the project author's, per the repo's convention of using the primary contact) on the `HttpClient` used for all EDGAR/data.sec.gov calls, and throttle client-side well under 10 req/s (a shared `SemaphoreSlim`/delay, since the limit is per source IP regardless of how many logical callers there are).

## 4. XBRL / inline XBRL structure — is structured data separable from prose?

**Yes, in two independent ways**, both confirmed from SEC's own material:

1. **Embedded in the same document (inline XBRL).** The primary `.htm` document *is* the XBRL instance: individual numeric/text facts are wrapped in `ix:nonFraction`/`ix:nonNumeric` (and related) tags directly inside the human-readable markup, each carrying a taxonomy concept (e.g. `us-gaap:Revenues`), context (period/entity/dimension), unit, and scale — "filers need only prepare one Inline XBRL document rather than generate an HTML document ... and then tag a copy of the data to create a separate XBRL exhibit." Viewers can "click on individual tagged data points in the filing" to see the concept, accounting-guidance citation, and reporting period. [SEC — Inline XBRL](https://www.sec.gov/data-research/structured-data/inline-xbrl) (Last Reviewed or Updated: **2025-01-17**).
2. **Extracted as a conventional, separate machine-readable instance.** Confirmed empirically from the Apple example: alongside the inline-XBRL primary document, the accession also contains `aapl-20250927_htm.xml` — a plain (non-inline) XBRL instance document that EDGAR's dissemination pipeline generates *from* the inline HTML — plus the full taxonomy/linkbase set (`.xsd`, `_cal.xml`, `_def.xml`, `_lab.xml`, `_pre.xml`). So a pipeline never has to parse `ix:` tags out of HTML by hand to get structured facts; the extracted instance (or the `companyfacts`/`companyconcept` JSON APIs, which are built from the same underlying tagged data) is available as a ready-made, HTML-parsing-free source of every tagged concept/value/period/unit in the filing.
3. **`R*.htm` rendered statements** (§2) are a third, human-readable-but-machine-generated middle ground: one file per financial statement/note, produced directly from the XBRL data by SEC's own renderer, indexed by `FilingSummary.xml`.

**Direct implication for the chunking pipeline:** yes — XBRL tags (via the extracted instance, the `companyfacts` JSON API, or the `R*.htm`/`FilingSummary.xml` rendering) can serve as **ground-truth metadata/anchors for financial-statement table chunks**, rather than relying on parsing merged cells and footnote markers out of the raw narrative HTML table. A concept like `us-gaap:Revenues` with its exact reported value, period, and unit is available as structured data independent of how messily the surrounding HTML renders it. The narrative prose sections of a 10-K (Item 1 Business, Item 7 MD&A, legal proceedings, risk factors, etc.) are **not** XBRL-tagged in the same granular way — only specific required disclosures (mostly the financial statements and certain structured items) carry `us-gaap`/company-extension tags — so this anchor strategy applies to the financial-statement portions of a filing, not the whole document; the rest still needs HTML-text chunking.

**Uncertain / could not verify:** the exact rule for which non-financial-statement narrative disclosures (if any) also get XBRL/iXBRL tagging beyond the core financial statements (e.g. certain cover-page and risk-factor-adjacent facts are tagged per the "Cover Page" taxonomy) — worth checking the specific taxonomy structure (`us-gaap` + `dei` namespaces) against an actual downloaded filing before assuming tag coverage boundaries.

## 5. Licensing / rate-limit / ToS constraints

- **Public, freely copyable, no permission needed.** SEC's own privacy-information page states plainly: **"Information presented on sec.gov is considered public information and may be copied or further distributed by users of the web site without the SEC's permission."** They ask (not require) appropriate citation: *"Please consider appropriate citation to the SEC as the source."* [SEC.gov — Privacy Information](https://www.sec.gov/about/privacy-information) (Last Updated: **2023-11-29**).
- As a U.S. federal government work, EDGAR filing text/data is consistent with the general 17 U.S.C. §105 public-domain rule for federal government works; the privacy-information page's plain-copy language is the SEC's own operative statement of this for sec.gov content, and is what this project can point to directly.
- **Trademark carve-out, not a data-licensing restriction:** "SEC," the EDGAR logo, and the names EDGAR/EDGARLink/EDGARLink Online are registered trademarks — don't use them in a product/trade name or domain implying SEC/EDGAR affiliation without a license. Using "EDGAR" descriptively (e.g. "ingests filings from SEC EDGAR") is fine; naming the product itself after EDGAR would not be.
- **Rate limit and User-Agent requirement are the only real technical gate** — see §3: 10 requests/second hard ceiling (monitored, enforced by temporary IP blocking), descriptive `User-Agent` with contact info required, no API key/auth. "Automated access must comply with SEC.gov's Privacy and Security Policy" per the API documentation page — this is the same 10 req/s + User-Agent policy, not a separate stricter one for APIs.
- **Practical note for a portfolio project:** since this project deliberately does one company/filer per tenant and Stage 2 is a one-time or low-frequency ingest (not continuous polling), staying an order of magnitude under 10 req/s with a real contact-email User-Agent fully satisfies the documented policy — no special agreement or registration is required for this scale of use.
