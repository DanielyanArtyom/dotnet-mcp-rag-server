# Debugging and testing a chunking pipeline before embeddings/retrieval exist

Question: Stage 2 builds ingestion + chunking for messy, table-heavy SEC EDGAR filings, with embeddings/retrieval not arriving until Stage 3/4. What concrete, practitioner-proven techniques let a solo dev validate chunk output is reasonable *before* there's a retrieval loop to eval against — and what does the eval-driven loop look like once retrieval exists (Stage 4, where this project already commits to a 20-30 question eval set)?

Sources current as of 2026-09-13.

## Recommendation

For Stage 2 specifically (no embeddings yet): **write every chunk plus its metadata (source doc, page/section, char offsets, token count) to a local file — JSON Lines or a SQLite table — and eyeball it**, the same low-ceremony pattern LlamaIndex's own node/document model and LangChain's own debug tooling assume you'll do ad hoc (there's no framework-blessed "chunk debugger" API in either — see Finding 1). Layer three cheap, code-only sanity checks on top, all computable with no LLM calls and no retrieval:

1. **Token-count histogram per chunk** (min/max/median/stddev) — catches a broken splitter producing near-empty or wildly oversized chunks. Not a named library feature; it's exactly the kind of check the [Chroma "Evaluating Chunking Strategies for Retrieval" research](https://www.trychroma.com/research/evaluating-chunking) implies is a prerequisite before their token-level IoU/precision/recall metrics mean anything (garbage-sized chunks poison every downstream metric).
2. **A programmatic "did this chunk end mid-sentence / mid-table" flag** — e.g. does the chunk's last non-whitespace char look like sentence-final punctuation, and for tables, does row/column structure survive intact. No official tool names this as a metric (see Finding 2) — treat it as a repo-local heuristic, not a citable industry standard.
3. **For the EDGAR table-heavy corpus specifically**, verify tables are never silently merged into surrounding prose or split across chunk boundaries mid-row — this is the one table-specific behavior a real chunking library documents and tests for (Unstructured — Finding 4).

For visual/manual inspection, run a handful of real EDGAR filings through **[ChunkViz](https://chunkviz.up.railway.app/)** (Greg Kamradt, MIT-licensed, [github.com/gkamradt/ChunkViz](https://github.com/gkamradt/ChunkViz)) or **LangChain's own [text-split-explorer](https://github.com/langchain-ai/text-split-explorer)** first, to build intuition for how a given chunk-size/overlap config behaves on real 10-K prose and tables, before writing your own chunker or wiring it into the Lumen pipeline. Both are paste-text-and-see-colored-chunks tools, not part of the .NET pipeline — used for exploration, not integration.

Once Stage 4 arrives and embeddings/retrieval exist, layer the RAGAS `LLMContextPrecisionWithReference` / `LLMContextRecall` metrics (Finding 3) or Azure AI Foundry's `Retrieval`/`Document Retrieval` evaluators (Finding 3) on top of the 20-30 question eval set already committed to in `CLAUDE.md` — chunking quality at that point is judged by its effect on those numbers, not by re-running the Stage 2 heuristics.

## Findings

### 1. Visual/manual inspection tooling

**No mainstream RAG framework ships a built-in chunk-boundary visualizer as part of its core API.** LlamaIndex's and LangChain's own docs describe chunking purely functionally (`SentenceSplitter`, `RecursiveCharacterTextSplitter`, etc. — [LlamaIndex node parser modules](https://docs.llamaindex.ai/en/v0.12.15/module_guides/loading/node_parsers/modules/), [LangChain recursive splitter guide](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter)); inspecting the resulting `Node`/`Document` objects is left to the developer printing/dumping them, not a dedicated debug UI in the library itself.

What *does* exist, from primary/official-adjacent sources:

- **[ChunkViz](https://chunkviz.up.railway.app/)** — built by Greg Kamradt, MIT license, repo at [github.com/gkamradt/ChunkViz](https://github.com/gkamradt/ChunkViz). Paste text, pick a splitter (character/recursive-character, in JS/Python/Markdown variants), set chunk size + overlap, and see each resulting chunk colored distinctly with overlaps highlighted. This is the same Kamradt behind the widely-cited "5 Levels of Text Splitting" notebook ([FullStackRetrieval-com/RetrievalTutorials](https://github.com/FullStackRetrieval-com/RetrievalTutorials/blob/main/tutorials/LevelsOfTextSplitting/5_Levels_Of_Text_Splitting.ipynb)), which explicitly recommends visual spot-checking as step one before any quantitative eval.
- **[text-split-explorer](https://github.com/langchain-ai/text-split-explorer)** — a Streamlit app published under the official `langchain-ai` GitHub org. Paste a text file, choose chunk size/overlap/splitter type, and see the resulting splits rendered. Hosted copy at [langchain-text-splitter.streamlit.app](https://langchain-text-splitter.streamlit.app/). **Caveat:** the repo shows as archived (Feb 2026) — still usable and citable as an official LangChain artifact, but not actively maintained; expect it to lag current `langchain-text-splitters` releases.
- **Notebook-based inspection** is the pattern LlamaIndex's own docs implicitly assume: their [Evaluating](https://developers.llamaindex.ai/python/framework/understanding/evaluating/evaluating/) and [Retrieval Evaluation](https://developers.llamaindex.ai/python/examples/evaluation/retrieval/retriever_eval/) guides are themselves Jupyter notebooks that print nodes/results inline rather than using any dedicated viewer widget — i.e., "print the objects in a notebook cell" is the documented workflow, not an anti-pattern to route around.
- Chroma (the vector-DB vendor) does **not** ship a chunk-boundary visualizer either; their chunking work ([Finding 2](#2-quantitative-pre-retrieval-signals)) is a research methodology, not a shipped debug tool.

### 2. Quantitative pre-retrieval signals

No primary source defines a single named "chunk quality score" computable without any retrieval or ground truth. What official/vendor sources do converge on:

- **[Chroma's "Evaluating Chunking Strategies for Retrieval"](https://www.trychroma.com/research/evaluating-chunking)** (Chroma's own research team) is the most rigorous primary source on chunking-specific (as opposed to general retrieval) evaluation. Their metrics — **Intersection-over-Union (IoU)** of retrieved vs. relevant tokens, token-level **Precision**/**Recall**, and **Precision_Ω** (an upper-bound precision assuming perfect recall) — are still fundamentally *retrieval* metrics (they require query/relevant-excerpt ground truth), not pre-retrieval sanity checks. They matter here as the target metric your Stage 2 heuristics are trying to protect: badly-sized or badly-cut chunks put a low ceiling on IoU/precision no matter how good retrieval later gets.
- **Pinecone's [Chunking Strategies for LLM Applications](https://www.pinecone.io/learn/chunking-strategies/)** treats chunk size explicitly as a hyperparameter to sweep empirically (their own phrase: evaluate chunk sizes "using multiple indices or namespaces with representative datasets") — again a retrieval-time comparison, not a standalone pre-retrieval metric.
- **No primary source names a "% chunks cut mid-sentence" or "% chunks cut mid-table" metric.** This is a real gap: every source that raises the problem (mid-sentence cuts hurting groundedness) frames it as a *design constraint to prevent via a good splitter* (e.g. sentence-boundary-aware splitting), not as a number to compute after the fact and report. Treat the "did this chunk end cleanly" check in the Recommendation as a project-local heuristic script, not an industry-standard metric — there is nothing authoritative to cite for it beyond "this is what sentence-aware splitters are supposed to guarantee by construction."
- What *is* concretely and repeatedly suggested as a first-pass sanity check, even if not formalized into one named metric: **chunk-count-per-document and token-count distribution**, checked simply so a broken parser (e.g. one that produces a single 50,000-token chunk for an entire 10-K, or thousands of 3-token chunks from over-aggressive table-row splitting) is caught immediately. This falls directly out of the Chroma paper's own premise — their evaluation corpus spans "financial reports, biomedical literature, chat logs, Wikipedia, government documents" specifically because dataset messiness (their word) skews chunk-size distributions unpredictably, which is exactly the SEC-filing risk this project is stress-testing against.

### 3. Eval-driven loop once retrieval exists (Stage 4 territory)

Once there's a retriever to query, three named, citable metric families recur across primary sources:

- **RAGAS** ([docs.ragas.io](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)) — the retrieval-relevant named metrics are **Context Precision** ([definition](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/): mean of precision@k across retrieved chunks, i.e. are relevant chunks ranked near the top) and **Context Recall** ([definition](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/): fraction of claims in the reference answer that are supported by the retrieved context). Generation-quality metrics in the same framework (Faithfulness, Response Relevancy) are separate and answer a different question (is the generated answer grounded in what was retrieved) — relevant to Stage 4's generation step, not chunking per se.
- **OpenAI Cookbook, "Evaluate RAG with LlamaIndex"** ([cookbook.openai.com](https://cookbook.openai.com/examples/evaluation/evaluate_rag_with_llamaindex), [notebook](https://github.com/openai/openai-cookbook/blob/main/examples/evaluation/Evaluate_RAG_with_LlamaIndex.ipynb)) — an official OpenAI cookbook entry, built on LlamaIndex's `RetrieverEvaluator`. Names **Hit Rate** (does the top-k retrieved set contain the expected chunk) and **MRR** (Mean Reciprocal Rank — rewards the expected chunk appearing higher in the ranking) as the two retrieval metrics, computed against a synthetic query→expected-chunk-id dataset generated by GPT-4 from the corpus itself. LlamaIndex's own [Retrieval Evaluation docs](https://developers.llamaindex.ai/python/examples/evaluation/retrieval/retriever_eval/) additionally list `precision`, `recall`, `ap` (average precision), and `ndcg` as selectable metric names on the same `RetrieverEvaluator.from_metric_names(...)` API.
- **Azure AI Foundry built-in RAG evaluators** ([learn.microsoft.com](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/rag-evaluators)) — draws a documented line between two evaluation modes that maps well onto this project's own two-eval-set structure:
  - **Process evaluation** (retrieval-only, no generation needed): `Retrieval` (LLM-judged relevance of retrieved chunks to the query, no ground truth needed) and `Document Retrieval` (requires human-labeled query-relevance judgments — "qrels" — and computes **Fidelity**, **NDCG**, **XDCG**, **Max Relevance**, and **Holes**, the last flagging documents with missing ground-truth labels).
  - **System evaluation** (needs a generated response): `Groundedness`/`Groundedness Pro` (response consistent with context — precision aspect), `Relevance` (response addresses the query), `Response Completeness` (response covers the ground truth — recall aspect).
  - This is a genuinely useful frame for Stage 4: `Document Retrieval`'s qrel-based metrics are the closest official analogue to "does chunking + retrieval find the right chunk," decoupled entirely from generation quality — worth building the 20-30 question eval set with per-question "which chunk(s) should be retrieved" labels in mind, not just a final expected-answer string, since that unlocks this style of pre-generation retrieval scoring for cheap ($0, no LLM-judge calls) in addition to the end-to-end answer eval.

### 4. Table-specific tooling

The one primary source that documents table-aware behavior as a first-class, tested concern is **Unstructured** ([chunking docs](https://unstructured.readthedocs.io/en/latest/core/chunking.html)): "*A `Table` element is always isolated and never combined with another element*" — tables are never silently merged into a surrounding prose chunk — and if a table is too large for one chunk, it's split via dedicated `TableChunk` elements rather than falling back to generic text-splitting logic. Their [Table Extraction from PDF](https://unstructured.readthedocs.io/en/main/best_practices/table_extraction_pdf.html) docs separately note that extraction quality (not chunking) is the harder problem for complex/nested tables — i.e., garbage-in from a bad table parse will look like a chunking bug even when the chunker did its job correctly, which is worth ruling out first when debugging a bad-looking EDGAR table chunk.

No RAG-evaluation framework (RAGAS, Azure AI Foundry, LlamaIndex's `RetrieverEvaluator`) has a table-specific metric or evaluator — tables are just retrieved/scored as regular text chunks once they're in the index. Table handling quality is validated at the chunking/extraction stage (visually, via Finding 1's tools, plus the isolation guarantee above), not at eval time.

### 5. Practical local-dev workflow for a solo developer, no UI

Given this project's stated aversion to unnecessary abstraction (per `CLAUDE.md`), the lowest-effort options that are still genuinely used in practice:

- **Dump chunks to JSONL, one line per chunk**, with `{ "docId", "chunkIndex", "text", "tokenCount", "charStart", "charEnd", "sourcePage"/"sourceSection" }` — trivially diffable across runs when a splitter parameter changes, greppable, and loadable into a throwaway LINQPad/`dotnet-script` snippet or even `jq` for the histogram check in the Recommendation. This is the same shape LlamaIndex's own `Node.metadata` dict and LangChain's `Document.metadata` use internally — i.e., dumping exactly what the frameworks already track as chunk metadata, just to a flat file instead of an in-memory object, costs nothing extra to design.
- **A local SQLite table** (`Chunks(Id, DocumentId, ChunkIndex, Text, TokenCount, CharStart, CharEnd, ...)`) is the natural next step once JSONL gets unwieldy to query — `sqlite3 chunks.db` from the terminal, or DB Browser for SQLite, gives ad hoc filtering ("show me every chunk under 20 tokens," "show me every chunk containing a `<table>` marker") without building any UI. Given Stage 3 already lands on Postgres, this could equally be a throwaway table in the dev Postgres container instead of a separate SQLite file — same idea, one less moving part.
- For the visual pass specifically, **paste 2-3 representative EDGAR excerpts (dense prose + a financial table) into ChunkViz or text-split-explorer** ([Finding 1](#1-visualmanual-inspection-tooling)) while tuning chunk size/overlap, before trusting the .NET pipeline's own output — cheaper than writing custom visualization code, and it's exactly the exploratory step both tools were built for.

## Uncertain / could not verify

- **No official/primary source names a standardized "% chunks cut mid-sentence" or "% chunks cut mid-table" metric.** Every source that discusses the problem treats clean boundaries as something a good splitter should guarantee by construction (sentence-boundary-aware splitting, Unstructured's table isolation), not something to measure after the fact with a named metric. Any such check in this project should be understood as a repo-local heuristic script, not a citable industry-standard signal.
- **RAG Chunk Inspector** ([gekro.com/apps/rag-chunk-inspector](https://gekro.com/apps/rag-chunk-inspector/), source at [github.com/drajb/gekro](https://github.com/drajb/gekro/tree/main/apps/web/src/components/apps/rag-chunk-inspector)) does exist and is MIT-licensed and does what it claims (paste text, visualize fixed/recursive/sentence-aware chunking with overlap highlighting) — but it's a single developer's personal-lab side project, not a "well-known" tool in the sense the research brief asked for. Mentioned here for completeness, not part of the Recommendation.
- Could not find any official LlamaIndex, LangChain, or Chroma documentation describing a **built-in, shipped** (as opposed to community-notebook) chunk visualization widget inside the framework itself — every tool found (ChunkViz, text-split-explorer) is a separate, standalone app that consumes the framework's splitters, not a feature of the framework's own API surface.
- The **Chroma evaluating-chunking paper's exact table/table-heavy-document handling** was not confirmed — the paper's stated corpus includes "government documents" and "financial reports" but the fetched summary didn't surface any table-specific finding distinct from their general token-level IoU/precision/recall methodology; if this matters later, the full paper (not just the landing page) should be read directly.
