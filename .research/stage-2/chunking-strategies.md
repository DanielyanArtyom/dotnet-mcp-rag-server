# Chunking strategy options for RAG — landscape survey

Sources current as of **2026-09-13**. Every claim is tied to a primary source (framework docs, official vendor docs, or the technique's original writeup); the source's own dated context is included where visible. This file covers chunking as a general RAG concept — not SEC EDGAR specifics or .NET library choices (covered elsewhere).

## 1. Fixed-size chunking with overlap

**LangChain — `RecursiveCharacterTextSplitter`.** The base `TextSplitter` class (which `RecursiveCharacterTextSplitter` inherits from) defaults to `chunk_size=4000`, `chunk_overlap=200` — i.e. a 5% overlap ratio at the class default. [`TextSplitter.__init__` — `langchain_text_splitters/base.py`](https://github.com/langchain-ai/langchain/blob/master/libs/text-splitters/langchain_text_splitters/base.py). In practice almost nobody ships the raw default: LangChain's own worked example in Microsoft's Azure AI Search chunking guide (see below) uses `chunk_size=1000, chunk_overlap=200` (20% overlap) after inspecting the actual token distribution of the source PDF. [Azure AI Search — Chunk Documents, "LangChain data chunking example"](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents) (`ms.date` 2026-06-08, updated 2026-08-31).

**LlamaIndex — `SentenceSplitter` / `TokenTextSplitter`.** Both default to `chunk_size=1024`, `chunk_overlap=20` (roughly a 2% overlap ratio) per the official node-parser module guide. [LlamaIndex — Node Parser Modules](https://developers.llamaindex.ai/python/framework/module_guides/loading/node_parsers/modules/). Note: some LlamaIndex API-reference pages for older versions show `chunk_overlap=200` for `SentenceSplitter` instead of 20 — the two documented defaults disagree across versions/pages, so treat "20" (current module guide) as the number to verify against the installed version rather than assume.

**Azure AI Search — Text Split skill.** This is the most rigorously quantified fixed-size default of anything found: the skill's `maximumPageLength` has a documented minimum of 300, maximum of 50,000, and a **default of 5,000 characters** in `pages` mode (its default `textSplitMode`). [Text Split Skill — Azure AI Search, "Skill Parameters"](https://learn.microsoft.com/en-us/azure/search/cognitive-search-skill-textsplit) (`ms.date` 2026-01-07, updated 2026-07-02). For embedding-oriented use, the same page notes "for text embedding models, a general recommendation for page length is 512 tokens."

Separately, Azure AI Search's own chunking how-to guide gives a concrete, benchmarked recommendation rather than just a code default: **"start with a chunk size of 512 tokens (approximately 2,000 characters) and an initial overlap of 25%, which equals 128 tokens"** for fixed-size chunking, and separately recommends `maximumPageLength=2000` / `pageOverlapLength=500` (also 25%) as sensible starting parameters for the Text Split skill specifically. [Azure AI Search — Chunk Documents, "Content overlap considerations"](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents) (`ms.date` 2026-06-08, updated 2026-08-31).

That same page publishes an actual chunk-count table from re-running the Text Split skill against a real 200-page PDF (NASA's *Earth at Night* e-book) at different settings — useful as a concrete illustration of how size/overlap tradeoffs play out on real text, not just a claim:

| `textSplitMode` | `maximumPageLength` | `pageOverlapLength` | Total chunk count |
|---|---|---|---|
| pages | 1000 | 0 | 172 |
| pages | 1000 | 200 | 216 |
| pages | 2000 | 0 | 85 |
| pages | 2000 | 500 | 113 |
| pages | 5000 | 0 | 34 |
| pages | 5000 | 500 | 38 |
| sentences | N/A | N/A | 13,361 |

The same page also warns that overlap has to be sized relative to actual content: in their worked example the document's pages average only 189 tokens (max 1,583), so blindly applying "2,000 characters / 500 overlap" would have produced *no visible overlap at all* on most pages — they instead used `chunk_size=1000, chunk_overlap=200` for that specific corpus. The general lesson stated directly: measure your corpus's real token distribution (e.g. with `tiktoken`) before picking chunk size, rather than copying a default.

**Why overlap at all:** Azure's guidance states the overlap exists specifically "to maintain continuity and context" across a chunk boundary and "ensures smoother transitions between chunks without excessive duplication," and separately notes the *shape* of overlap needed varies by content type — "highly structured data might require less overlap, while conversational or narrative text might benefit from more." [Azure AI Search — Chunk Documents](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents).

**Summary of concrete numbers found:**

| Source | Default/recommended chunk size | Default/recommended overlap | Overlap % |
|---|---|---|---|
| LangChain `TextSplitter` base class default | 4000 chars | 200 chars | 5% |
| LangChain worked example (Azure doc) | 1000 chars | 200 chars | 20% |
| LlamaIndex `SentenceSplitter`/`TokenTextSplitter` default | 1024 tokens | 20 tokens | ~2% |
| Azure AI Search Text Split skill code default | 5000 chars | not set by default (0 if unset) | — |
| Azure AI Search recommended starting point | 512 tokens (~2000 chars) | 128 tokens (25%) | 25% |
| Azure AI Search Text Split skill recommended params | 2000 chars | 500 chars | 25% |

## 2. Sentence/paragraph-boundary-aware ("recursive") chunking

The dominant implementation pattern across frameworks is a **fallback chain of separators, tried in order from "biggest structural unit" to "smallest,"** so that a chunk boundary lands on the most semantically meaningful break available given the size budget.

**LangChain `RecursiveCharacterTextSplitter`** documents its default separator list as `["\n\n", "\n", " ", ""]` and states directly: "This has the effect of trying to keep all paragraphs (and then sentences, and then words) together as long as possible, as those would generically seem to be the strongest semantically related pieces of text." [LangChain — Recursive text splitter integration guide](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter). Concretely: it first tries to split only on blank lines (paragraph breaks); if a resulting piece still exceeds `chunk_size`, it retries that piece splitting on single newlines; if still too big, on spaces; and only as a last resort mid-word (empty-string separator, i.e. hard character cut).

**Azure AI Search Text Split skill** offers an explicit, simpler two-mode version of the same idea rather than a full recursive chain: `textSplitMode: sentences` splits purely on sentence-ending punctuation (language-dependent, controlled by `defaultLanguageCode`), while `textSplitMode: pages` (the default) targets a character/token budget but "attempts to avoid truncating a sentence, so the actual length might be smaller [than `maximumPageLength`]." [Text Split Skill — Azure AI Search](https://learn.microsoft.com/en-us/azure/search/cognitive-search-skill-textsplit).

**LangChain `MarkdownHeaderTextSplitter`** is the structure-aware variant one level up from sentence/paragraph splitting: it splits on Markdown heading syntax (`#`, `##`, `###`, configurable per level) rather than blank lines, which is the mechanism Microsoft's own Document Intelligence RAG guide recommends pairing with Document Intelligence's Markdown output — extract structure first (headings), then split along it. [Retrieval-Augmented Generation (RAG) with Azure Document Intelligence](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/retrieval-augmented-generation?view=doc-intel-4.0.0) (`ms.date` 2026-08-15), which shows this LangChain loader/splitter pairing directly in its own code sample.

**LlamaIndex's equivalent to "recursive" splitting is `SentenceSplitter`**, described in the official module guide as respecting sentence boundaries rather than doing an arbitrary character cut, and it is the parser LlamaIndex recommends as the general-purpose default (it's what `chunk_size`/`chunk_overlap` on the global `Settings` object configure implicitly). [LlamaIndex — Node Parser Modules](https://developers.llamaindex.ai/python/framework/module_guides/loading/node_parsers/modules/).

## 3. Semantic chunking (embedding-similarity breakpoints)

**Origin of the technique:** LlamaIndex's own documentation attributes the algorithm to Greg Kamradt's "5 Levels Of Text Splitting" video tutorial, not to LlamaIndex itself: their `SemanticSplitterNodeParser` pack description states it "implements the semantic chunking algorithm first proposed by Greg Kamradt in his Five Levels of Text Splitting tutorial." [`llama-index-packs-node-parser-semantic-chunking` — PyPI](https://pypi.org/project/llama-index-packs-node-parser-semantic-chunking/); cross-referenced against the current core docs, [LlamaIndex — Semantic Chunker example](https://developers.llamaindex.ai/python/examples/node_parsers/semantic_chunking/).

**How it works (per LlamaIndex's own description):** rather than a fixed size, the splitter "adaptively picks the breakpoint in-between sentences using embedding similarity, ensuring that a chunk contains sentences that are semantically related to each other." Mechanically: split the source into individual sentences, embed each one, compute the cosine similarity between each adjacent pair (or a windowed group, controlled by a `buffer_size` lookahead parameter — "how many sentences ahead the strategy peeks when deciding where to cut"), and cut wherever similarity drops sharply — the cut threshold is set via `breakpoint_percentile_threshold` (a dissimilarity percentile; lower values produce more/smaller chunks). [LlamaIndex — Node Parser Modules](https://developers.llamaindex.ai/python/framework/module_guides/loading/node_parsers/modules/).

**Documented caveats, directly from LlamaIndex's own docs:**
- **Tuning burden:** "You may have to tune the breakpoint percentile threshold" — there is no universal default that works well across corpora; the worked example itself uses `breakpoint_percentile_threshold=95` as a starting point, not a general recommendation.
- **Language limitation:** the sentence-boundary regex "primarily works for English sentences," limiting applicability to other languages without adaptation.
- **Cost, implicit rather than stated as a number:** the technique requires computing one embedding per sentence purely to *find* chunk boundaries, before the chunks themselves are ever embedded for retrieval — i.e., roughly double (or more, for short sentences) the embedding-API calls/cost of fixed-size chunking, which needs zero embedding calls until retrieval-time indexing. LlamaIndex's docs don't quantify this cost multiplier or publish a retrieval-quality delta versus `SentenceSplitter`; no primary-source benchmark number for "how much better semantic chunking retrieves" was found in official docs (see Uncertain section).

**Net practical read:** semantic chunking is the highest-effort/highest-cost option of the three general-purpose strategies (fixed-size, recursive/boundary-aware, semantic) and its payoff is not quantified by the framework that ships it — it is presented as a technique to try, not as a benchmarked upgrade.

## 4. Table-aware / structure-aware chunking

This is the most directly relevant section for SEC filings specifically (financial statements are dense tables), even though this file stays general.

**Unstructured.io** treats tables as atomic, protected units by design, not as flowing text to be cut like paragraphs: "A `Table` element is always isolated and never combined with another element" during chunking. If a single table's extracted text is larger than the configured `max_characters` limit, it is split into `TableChunk` elements via text-splitting (i.e. only split as a last resort, and only within itself, never merged with surrounding prose). Both of Unstructured's chunking strategies — `basic` (packs elements to a size budget) and `by_title` (also closes a chunk at every `Title` element to respect section boundaries, with a `combine_text_under_n_chars` setting to avoid over-fragmenting tiny sections) — inherit this "never merge tables with other elements" rule. [Unstructured — Chunking](https://docs.unstructured.io/open-source/core-functionality/chunking).

**Azure AI Document Intelligence (Layout model)** takes a different approach: rather than treating a table as an indivisible blob, it extracts the table's structure (rows/columns) and can output the whole document — prose and tables together — as a single **Markdown** document, with tables rendered as proper Markdown tables (columns/rows/alignment preserved). Microsoft's own guidance frames this explicitly as the mechanism for RAG chunking of table-heavy content: "you can use the Markdown content from the Layout model to split documents based on paragraph boundaries, **create specific chunks for tables**, and fine-tune your chunking strategy to improve the quality of the generated responses." It also states the Markdown output format is "LLM friendly" specifically because "you can turn any table in a document into Markdown format and avoid extensive effort parsing the documents for greater LLM understanding." [Retrieval-Augmented Generation (RAG) with Azure Document Intelligence](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/retrieval-augmented-generation?view=doc-intel-4.0.0) (`ms.date` 2026-08-15, updated 2026-08-14). Separately, Azure's Document Intelligence Layout model reference confirms it extracts tables (alongside titles, section headings, key-value pairs) as a first-class structural element type, not merely OCR'd text. [Document layout analysis — Document Intelligence](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout).

**Azure AI Search's own chunking guide** puts semantic/structure-aware chunking (of which table-aware chunking is a subset) in a distinct row of its chunking-technique comparison table from plain fixed-size or sentence-based splitting, explicitly listing "Azure Content Understanding skill (semantic chunking with markdown output)" as the built-in mechanism for chunks that "preserve context and semantic relationships across sentences and paragraphs" and "can span page boundaries." [Azure AI Search — Chunk Documents, "Common chunking techniques"](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents).

**Three distinct strategies in the wild, summarized:**
1. **Keep tables atomic / never split across a chunk boundary** — Unstructured.io's default behavior; a table only gets internally sub-split if it alone exceeds the max chunk size.
2. **Flatten to Markdown alongside prose, then chunk the combined Markdown** — Azure Document Intelligence's approach; tables become part of the same structured text stream as headings/paragraphs and get chunked using the same heading/paragraph-aware splitter (e.g. LangChain's `MarkdownHeaderTextSplitter`, shown directly in Microsoft's own sample code).
3. **Summarize the table separately** (not directly documented by a primary source in this survey) — mentioned in secondary/blog literature as a third option (attach an LLM-generated natural-language summary of a table as its own retrievable chunk, keeping the raw table as reference/metadata) but no official framework doc describing this as a first-class supported mode was found; flagged in Uncertain section below.

## 5. Metadata to attach per chunk

**LlamaIndex** treats `metadata` as a first-class dictionary on both `Document` and `Node` objects, plus a separate `relationships` dictionary tracking links between nodes (e.g. a node's parent document, or its neighboring nodes). Its documented propagation rule: "every Node derived from a Document will inherit the same metadata from that Document (e.g. a `file_name` field in the Document is propagated to every Node)" — i.e. the framework's own convention is to attach document-level metadata (like a filename) once on the source `Document` and let every chunk automatically carry it, rather than re-specifying it per chunk. [LlamaIndex — Documents and Nodes](https://developers.llamaindex.ai/python/framework/module_guides/loading/documents_and_nodes/). In practice, common fields LlamaIndex's own loaders populate include `file_name` and `page_label` (from `SimpleDirectoryReader`/PDF loaders) — i.e. source-document id and page number are the baseline, framework-populated metadata, with anything else (section heading, filing date, company, chunk index) left for the caller to add manually via each `Document`'s `metadata` dict.

**LangChain's `Document`** schema is deliberately minimal at the base-class level: `page_content` (the chunk's text) plus a free-form `metadata` dict, illustrated in the framework's own reference example as `metadata={"source": "https://example.com"}` — i.e. LangChain's convention is that `source` (where the content came from) is the one metadata key treated as near-universal by convention across loaders, with everything else (page number, section, custom fields) left to the specific document loader or the caller to populate. [LangChain — `Document` reference](https://reference.langchain.com/python/langchain-core/documents/base/Document). LangChain's own loader outputs shown in Microsoft's Azure AI Search chunking guide (`PyPDFLoader`) confirm this pattern concretely — each split chunk carries `metadata={'source': './data/earth_at_night_508.pdf', 'page': 9}`, i.e. source path + page number as the two fields a standard loader attaches per chunk before any custom enrichment. [Azure AI Search — Chunk Documents, "LangChain data chunking example"](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents).

**Azure AI Search's Text Split skill** outputs positional metadata as first-class, separate arrays alongside the chunk text itself: `offsets` (the chunk's start offset in the source, in UTF-8/UTF-16/CodePoint encodings), `lengths`, and `ordinalPositions` (the chunk's sequential position/index within the document). [Text Split Skill — Azure AI Search, "Skill Outputs"](https://learn.microsoft.com/en-us/azure/search/cognitive-search-skill-textsplit). This is a useful reference point for a minimum viable metadata schema: chunk index/ordinal position and byte offset are treated as standard, automatically-produced fields by Azure's own built-in skill, not something a caller must invent.

**Synthesizing a standard-practice minimum set** across all three official sources above: source document id/filename, some form of position marker (page number, byte offset, and/or chunk ordinal index), and a free-form dict for anything domain-specific. None of the three frameworks' official docs specify "heading/section title" or "filing date"/"company" as framework-populated defaults — those are consistently left to the caller to add as custom metadata keys, which matches this project's plan to add filing-specific fields (company/tenant, filing date, section) on top of the framework-level baseline.

## 6. Chunk size vs. embedding context limits and retrieval quality

**Hard limits from the embedding provider:** OpenAI's own embeddings guide states all three of its current embedding models — `text-embedding-3-small`, `text-embedding-3-large`, and `text-embedding-ada-002` — share the same **8,192-token maximum input** per embedding call. [OpenAI — Embeddings guide](https://developers.openai.com/api/docs/guides/embeddings). Azure AI Search's own chunking guide independently states the same figure for `text-embedding-3-small` ("the maximum length of input text ... is 8,191 tokens") and adds a rule of thumb for converting that to a word/character budget: "each token is around four characters of text for common OpenAI models, this maximum limit is equivalent to around 6,000 words of text." [Azure AI Search — Chunk Documents](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents). Practically, this ceiling is far above any of the chunk sizes discussed in section 1 (512–5,000 characters / ~150–1,000 tokens) — it constrains "don't embed an entire multi-hundred-page filing as one chunk," not the actual chunk-size choice, which is driven by retrieval granularity, not by hitting the model's hard limit.

**Retrieval-quality guidance (qualitative, not a published benchmark number):** neither OpenAI's nor Azure's own docs publish a quantified precision/recall-vs-chunk-size curve as a primary-source benchmark. What Azure AI Search's chunking guide does say, directly: "Chunking is only required if the source documents are too large for the maximum input size imposed by models, but it's also beneficial if content is poorly represented as a single vector" — i.e. even well under the token ceiling, a chunk that mixes multiple sub-topics produces a less useful embedding (the vector becomes a blurred average of unrelated content), which is the qualitative mechanism by which chunk size affects retrieval precision. The same page's stated factors to weigh: "Shape and density of your documents" (denser, more structured content can tolerate/needs different sizing than narrative prose), and the requirement to "find a chunk size that works best for all of the models you're using" when the same chunks feed both summarization and embedding models with potentially different practical sweet spots. [Azure AI Search — Chunk Documents, "Factors for chunking data"](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents).

Azure Document Intelligence's RAG guide makes the same qualitative tradeoff explicit for the fixed-size-vs-semantic choice specifically: fixed-size chunking "isn't recommended for text that requires semantic understanding and precise context. The fixed-size nature of the window can result in severing words, sentences, or paragraphs impeding comprehension and disrupting the flow of information," whereas semantic chunking "has the distinct advantage of maintaining semantic consistency within each chunk" at the cost of "significant computational[ly] algorithmically complex resources." [Retrieval-Augmented Generation (RAG) with Azure Document Intelligence](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/retrieval-augmented-generation?view=doc-intel-4.0.0).

## Uncertain / could not verify

- **No official, quantified precision/recall-vs-chunk-size benchmark was found from any primary source** (OpenAI, Azure, LangChain, or LlamaIndex). All guidance found is qualitative ("smaller chunks are more precise but lose context," "larger chunks preserve context but dilute the embedding") rather than backed by a published number (e.g. "recall drops X% when chunk size exceeds Y tokens"). Any such number would need to come from the project's own eval set (Stage 4), not from vendor docs.
- **LlamaIndex's documented default `chunk_overlap` for `SentenceSplitter`/`TokenTextSplitter` is inconsistent across its own pages** — the current module guide states 20, while some still-published API-reference pages for earlier versions state 200. Treat "20" as current-version-likely but verify against the actual installed package version before relying on it.
- **"Summarize the table as its own chunk" as a distinct, officially-documented table-chunking mode** — this pattern is discussed in secondary/blog sources but no primary framework doc (LlamaIndex, Unstructured, Azure Document Intelligence) was found describing it as a supported first-class strategy in the way "keep atomic" (Unstructured) and "flatten to Markdown" (Document Intelligence) are documented. Flagged as a real technique people use, but not primary-sourced here.
- **No official retrieval-quality comparison of semantic chunking vs. fixed-size/recursive chunking was found**, quantified or otherwise, from LlamaIndex or any other primary source in this survey — the "marginal gain" question from the task brief could not be answered with a citable number. LlamaIndex's own docs present semantic chunking as a technique to try, not as a benchmarked improvement.
- **LangChain's `Document.id` field** (whether it's populated by default, and by what) was not confirmed from the fetched reference page — the fetch returned only `page_content` and `metadata` with confidence; `id` appears in the class's API surface but its default-population behavior wasn't independently verified here.
