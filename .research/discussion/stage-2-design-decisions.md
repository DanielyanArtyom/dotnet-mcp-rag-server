# Stage 2 — журнал дизайн-решений (brainstorming, 2026-09-13 … 09-16)

Зачем файл: чтобы можно было перепроверить, *почему* сделано так, а не иначе. Итоговая спека — `.research/stage-2/design.md`; здесь — ход обсуждения: вопрос → варианты → решение → причина (по словам пользователя, где она была) → когда пересматривать. Это не стенограмма.

## Вводная
Пользователь не знал ни домен (SEC EDGAR), ни как чанкать и тестировать, и хотел сначала «всё узнать», потом сформулировать требования. Поэтому порядок был такой: 4 параллельных research-файла (`.research/stage-2/*.md`) → ручная разведка пользователя на реальных filing'ах (см. `stage-2-hands-on-findings.md`) → brainstorming → `design.md` → `plan.md` → реализация.

## Решения по порядку

| # | Вопрос | Решение | Причина / что сказал пользователь | Пересмотреть, если |
|---|--------|---------|-----------------------------------|--------------------|
| 1 | Как документ попадает в систему | **Upload** файла через API, без прямой интеграции с EDGAR API | «просто для теста… понять работает ли MCP сервер»; плюс после загрузки можно чистить/нормализовать данные | Понадобится автоматически тянуть filing'и по CIK (User-Agent + лимит 10 req/s из research) |
| 2 | Как хранить «чанк-таблицу» vs «обычный» | **Один универсальный `DocumentChunk`** + enum `ChunkType` (`Prose`/`Table`) | «в будущем могут вместо таблиц быть что-то другое» — enum расширяется, новая сущность не нужна | Появятся поля, свойственные только таблицам (row/column метаданные) |
| 3 | Хранить ли сырой файл | **Да**, чтобы пересчитывать чанки без повторной загрузки | Подход к чанкингу будет итерироваться (это уже стало ясно на ручных тестах) | — |
| 4 | Поля `Document` | Добавить `RawFilePath`, `FilingDate`; **`FormType` не добавлять** | «если решим использовать приложение в другой сфере, там такого не будет»; компания и так задаётся тенантом | Понадобится фильтровать по типу отчёта |
| 5 | `RawFilePath`: колонка с текстом или путь | **Путь к файлу**, сам файл на диске приложения | «файлы будут у нас на сервере (в папке приложения)»; запасной вариант — хранить в БД | Stage 6: локальный диск на Azure App Service не переживает рестарт/масштабирование → Blob Storage |
| 6 | Где на диске | `{DocumentStorage:RootPath}/{TenantId}/{DocumentId}.{ext}`, корень из appsettings, **не `wwwroot`**, в БД относительный путь | Файлы вне EF-фильтра → изоляция тенантов на диске держится только кодом; подпапка на тенанта — defense-in-depth | Переезд на Blob |
| 7 | Промежуточная модель нормализации | **Вариант B**: типизированный `List<DocumentElement>` (`Heading`/`Paragraph`/`Table`), содержимое таблицы — уже читаемый текст | Варианты: A — плоская строка + метки-сентинелы; C — Markdown как общий формат. Выбрано B, потому что формат входного файла отделяется от чанкера (см. #8) | Появятся типы, которым нужна структура строк/ячеек |
| 8 | Форматы входа | **HTML и PDF сразу**, за интерфейсом `IDocumentReader`; тип определяется по расширению через `FileExtensionContentTypeProvider` | Пользователь вспомнил `MimeTypeHelper` из Bookize (там тоже расширение → MIME); идея: «а вдруг для 3-го тенанта это меню ресторана» — конвейер не должен знать про SEC | Понадобятся DOCX/EPUB/TXT — добавляется ещё один reader |
| 9 | Насколько точно для PDF-таблиц | **Полноценно** (восстановление по координатам слов), а не упрощённо | «нет, делаем полноценно… 10-K/Q мы взяли, потому что сложно найти эти данные, и поймём, работает ли MCP» | Реальные PDF покажут, что эвристика не годится |
| 10 | HTML-библиотека | **AngleSharp** (не HtmlAgilityPack) | Реальные файлы «грязные» по стилям, но не битые по структуре; нужен `querySelector` для обхода `<table>` | На реальных файлах DOM окажется неработоспособным |
| 11 | Чанкер | Свой обход `DocumentElement`; проза — через `Microsoft.SemanticKernel.Text.TextChunker` (токены, overlap), таблица — атомарный чанк, огромная таблица делится по строкам; токены — `Microsoft.ML.Tokenizers` (cl100k) | Не писать самим токен-бюджет и overlap; таблица не должна резаться посередине (на ChunkViz это уже видели) | Stage 4 покажет провал по таблицам |

| 15 | Тесты | Unit (ридеры, чанкер) + integration (upload→chunks, изоляция тенантов для чанков) + характеризационный тест на реальном Apple 10-K; фикстуры коммитим в тестовый проект, не читаем из gitignored `.research/` | Изоляция — обязательный deliverable, как в Stage 1 | — |

## Две вещи, где ассистент возражал (и пользователь принял)
- `chunk size 162` символа при ручном тесте — слишком мало (≈30 токенов; ≈ тысячи микро-чанков на целом документе), overlap 3–5 символов — не overlap. После повторной проверки на 500/1000/1500 при 25% пользователь остановился на ~1000 символов.
- Файл JPMorgan, который пользователь сначала открыл, оказался **424B2** (проспект structured note), а не 10-K/10-Q. Разбор по нему не репрезентативен для корпуса Stage 2; правильные ссылки нашли через `data.sec.gov` (`CIK 19617`).
