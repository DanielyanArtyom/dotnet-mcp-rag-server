## Предложенный scope этапа (к уточнению на brainstorming)

1. Eval-сет 20–30 вопросов **первым**, до оптимизаций: эталонный ответ + метка чанка/раздела + категория (проза-перефраз, значение из таблицы, точный термин, 10-K vs 10-Q, вопрос без ответа, ловушка чужого тенанта).
2. Eval-харнесс: hit@k, MRR (retrieval, $0) + корректность ответа.
3. `POST /api/ask`: retrieval → сборка контекста (нумерованные источники, бюджет токенов) → `IChatClient` (MEAI) → ответ со ссылками. Параметры генерации в конфиге. Fake chat-клиент для тестов (сборка и тесты зелёные без Azure, как в Stage 3).
4. Рычаги, каждый — только после замера: гибрид (Postgres FTS + RRF), параметры чанкинга, topK, возможно HNSW.

## Эксперименты пользователя (E0–E7)

E0 baseline (vector-only) → E1 разбор провалов по категориям → E2 гибрид → E3 чанкинг 250/60 vs 400/100 vs 150/40 → E4 topK контекста 3/5/10 → E5 temperature/top-p (стабильность, ×3 прогона) → E6 промпт и отказ на вопросах без ответа → E7 HNSW (опционально; вероятно «не нужен, exact = N мс»).

Гипотезы (не обещания): vector-only слаб на таблицах/числах/точных терминах — там выигрывает гибрид; точность ответа ниже hit@k из-за дефектов таблиц Stage 2 (нет строки заголовков у поделённой таблицы, выброшенные пустые ячейки, разорванные `$ | 45,781`); латентность доминирует генерация.

## Вопросы для research

- У OpenAI/Azure chat API, по-видимому, нет sampling-параметра `top_k` (в `CLAUDE.md` он упомянут) — проверить; реальный top-k у нас — retrieval.
- Reasoning-модели не принимают `temperature` — влияет на выбор mini-модели.
- Postgres FTS (`tsvector`, словарь, ранжирование) + RRF — как стыковать с сырым SQL и тенант-предикатом.
- Методика eval: метрики retrieval (hit@k, MRR), оценка ответа (точное совпадение чисел vs LLM-judge).
- HNSW + фильтр по тенанту (iterative scans / partial index / партиционирование) — уже частично в `stage-3/pgvector-and-dotnet.md`.
