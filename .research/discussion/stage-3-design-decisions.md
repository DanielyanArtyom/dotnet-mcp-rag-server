# Stage 3 — журнал дизайн-решений (brainstorming, 2026-09-20)

Зачем файл: чтобы позже можно было перепроверить, *почему* сделано так. Итоговая спека — `.research/stage-3/design.md`; research, на который она опирается — три файла в `.research/stage-3/`. Это не стенограмма, а «вопрос → решение → причина → когда пересматривать».

## Вводная

Пользователь сформулировал рамку одной фразой: **«часть с Azure пока пропускаем — приготовь всё что нужно, а после я включу Azure и тогда сможем тестировать»**. Из неё выросло главное ограничение этапа: сборка и все тесты должны быть зелёными без единого ключа, а включение Azure — только правка конфига. Порядок работы — как на Stage 2: research → brainstorming → design.md → plan.md → реализация.

## Три находки research'а, которые изменили дизайн

1. **`Azure.AI.OpenAI` не нужен.** Его последняя стабильная версия — 2.1.0 (декабрь 2024, собрана против `OpenAI 2.1.0`), а `Microsoft.Extensions.AI.OpenAI 10.10.0` требует `OpenAI >= 2.13.0`; всё между — беты. При этом Azure OpenAI **v1 API GA с августа 2025**: обычный `OpenAIClient` с `Endpoint = .../openai/v1/`, без `api-version`, с автообновлением токена Entra ID прямо в OpenAI-клиенте. Один пакет вместо двух и готовая история для managed identity на Stage 6.
2. **pgvector индексирует только до 2000 измерений** (хранит до 16000). Значит `text-embedding-3-large` (3072) в Stage 4 нельзя проиндексировать HNSW без `halfvec`. На exact search Stage 3 не влияет, но это довод за 1536.
3. **Свой README pgvector предупреждает про мультитенантность:** общий ANN-индекс между тенантами портит recall соседям, а фильтр при ANN применяется *после* сканирования индекса (при `ef_search = 40` и условии, которому отвечает 10% строк, в среднем останется 4 строки). Это заготовка для решения Stage 4: iterative scans vs partial index vs партиционирование — и измерять, а не предполагать.

## Что осталось открытым

ANN-индекс и его взаимодействие с тенант-фильтром (Stage 4); кэш эмбеддингов; хвосты Stage 2 (приблизительные `CharStart/CharEnd`, потеря строки заголовков при делении таблицы, пустые ячейки, некалиброванная PDF-эвристика, необобщённая склейка `$`/`%`) — Stage 3 их не чинит, но делает их видимыми: плохой чанк теперь виден как плохой результат поиска.

## Что пойдёт в `DECISIONS.md` после этапа

Только с цифрами: время загрузки с эмбеддингом против 0,75 с из Stage 2, латентность точного поиска на реальном объёме чанков и — уже после включения Azure — выживает ли чанкинг 250/60 при контакте с настоящим retrieval.
