# Stage 2 — наблюдения пользователя на реальных filing'ах (ручная разведка)

Это материал самого пользователя (интервью-нарратив «пробовал → увидел → понял → решил»). Ссылки и файлы: `samples/edgar/` (в `.gitignore`).

## Выбор корпуса
- Два тенанта, максимально непохожих: **Apple Inc.** (CIK 320193, «чище») и **JPMorgan Chase & Co.** (CIK 19617, банк, тяжёлые таблицы). Выбран вариант «Apple + JPMorgan» из трёх предложенных.
- Apple: 10-K `aapl-20250927.htm` (accession 0000320193-25-000079), 10-Q `aapl-20260627.htm` (0000320193-26-000020).
- JPMorgan: 10-K `jpm-20251231.htm` (0001628280-26-008131, подан 2026-02-13), 10-Q `jpm-20260630.htm` (0001628280-26-054343). Первоначально по ошибке открыт `form424b2.htm` (проспект structured note): файлов такого типа у JPMorgan сотни в год, поэтому без фильтра `Forms=10-K` в поиск попадают именно они. Оставлен как «образец максимального мусора».
- Поиск: `https://www.sec.gov/edgar/search/` — поле **Company** (не основная строка запроса) + фильтр **Forms**.

## Что «грязный HTML» значит на практике
- Сначала пользователь смотрел **отрендеренную** страницу и решил, что всё понятно. Поправка: «грязь» видна только в **исходнике** (View Source / редактор) — браузер её скрывает.
- Реальные паттерны, найденные в исходнике:
  - пустые `<div>` с одним `<br/>` и inline-стилями (`margin-top:9pt…`, у JPM — `min-height:42.75pt;width:100%`);
  - `&#160;` (nbsp) вместо пробелов, `&amp;`, `&#8220;` (кавычки);
  - пустые `<td colspan="3" style="padding:0 1pt">` для выравнивания;
  - в проспекте 424B2: `<p>` внутри `<td>`, десятки inline `font-style`/цветов на каждом фрагменте;
  - вложенные `<table>` — у Apple не нашёл, у JPM ожидалось больше.
- Вывод пользователя: HTML **нужно чистить до чанкинга**; при этом 1 строка в файле = вся разметка.
- Вывод про XBRL: пользователь прогнал файлы через `tidy` (`-w 120 -i`, `&nbsp;` → числовые сущности) — тот отбросил нестандартные `ix:*` теги (~2000 предупреждений), пострадал только скрытый `display:none` блок с XBRL-метаданными. Значит **очистка текста и извлечение XBRL-фактов — два разных шага на разных версиях файла**; если XBRL понадобится, парсить оригинал отдельным парсером.
- Решение по XBRL/`R*.htm`: пока **не использовать**, «проще всё в одном месте (HTML)», а `R*` — отдельные ссылки. Компромисс (осознанный): платим ручной обработкой мусора в таблицах.

## ChunkViz-эксперименты
- Проза (абзацы MD&A / Income Taxes / Controls): **500 / 1000 / 1500 символов при overlap 25%** — «всё выглядело отлично», лучший — **~1000**. (Первый заход на 162 символа/overlap 3–5 был слишком мелким — см. `stage-2-design-decisions.md`.)
- Таблица (Segment Operating Performance, Apple): при копировании из рендера строки теряют разделители («гэпы между текстом и цифрами»), а символьный сплиттер **режет таблицу посередине** — цифры отрываются от подписей регионов. Это и стало эмпирическим аргументом за «таблица = неделимый атом».
- JPMorgan 10-Q: `1000/250` даёт нормальный текст, но пока в HTML мусор, «ничего путного не будет» — то есть узкое место в **HTML → чистый текст**, а не в цифрах чанка. Этот вывод изменил приоритет в дизайне: нормализация первична, размеры вторичны.

## Прикладные факты, вынесенные из research (для памяти)
- EDGAR: основной документ — inline-XBRL HTML (HTML 3.2/4.0-подмножество, `<table>` используется и для данных, и для вёрстки); PDF — только courtesy-копия; accession-папка — десятки файлов (`R*.htm`, `FilingSummary.xml`, …).
- API `data.sec.gov`: без ключа, обязателен осмысленный `User-Agent`, лимит 10 req/s.
- Лицензия: контент публичный; ограничение — только на использование торговых знаков SEC/EDGAR в названии продукта.
