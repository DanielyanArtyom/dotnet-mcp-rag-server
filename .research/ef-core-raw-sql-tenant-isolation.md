# EF Core global query filters vs raw SQL — what actually bypasses tenant isolation

Sources current as of **2026-09-09**.

## Decision

Lumen's vector similarity query is written with **unmapped `SqlQuery<T>`/`ExecuteSqlRaw` (or Dapper)**, not composable `FromSqlRaw` over a mapped entity — this is the specific mechanism that genuinely bypasses EF Core's global `TenantId` query filter, and it's justified by needing session-level HNSW tuning (`SET LOCAL hnsw.ef_search = ...`) that no LINQ-based vector API exposes. The tenant-isolation integration test (two tenants, assert no cross-tenant leakage) targets this exact path.

## The nuance

**The project's original premise ("EF Core global query filters do NOT apply to raw SQL / `FromSqlRaw`") is only partially true, and the distinction matters for designing an honest test.**

- Behavior changed across EF Core versions: EF Core 2.x applied filters to `FromSql`; EF Core 3.x removed them; **starting in EF Core 5.0 preview 7, global query filters are applied by default to `FromSqlRaw`/`FromSql` again**, as long as the raw SQL is *composable* (EF Core can wrap it as a subquery and add the filter's `WHERE` around it) — `.IgnoreQueryFilters()` is required to opt out. [dotnet/efcore issue #21854](https://github.com/dotnet/efcore/issues/21854) (official EF Core repo).
- Official docs confirm composability rules: `FromSql`/`FromSqlRaw` results can be composed with LINQ (`.Where()`, `.Include()`, etc.) as long as the SQL is a plain composable `SELECT` (no trailing semicolon, no non-subquery-legal hints/`ORDER BY`, not a stored procedure). [SQL Queries — EF Core | Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/querying/sql-queries) (`ms.date` 2022-09-19, updated 2026-09-03). The query-filter-applies claim itself is sourced from the GitHub issue above, not restated on this docs page.
- **Where the premise holds cleanly:** a hand-written vector similarity query typically returns a projection (id + computed distance column), not the full mapped entity — so the natural API is `context.Database.SqlQuery<TDto>(...)` (unmapped type) or raw `ExecuteSqlRaw`/a bare `DbConnection`/Dapper call. None of these are tied to a mapped entity type, so **there is no query filter to apply in the first place.** This is a distinct API from `FromSql`/entity queries. [SQL Queries — EF Core | Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/querying/sql-queries). Mechanism is identical on SQL Server and PostgreSQL — provider-agnostic EF Core behavior.
- **Surprising finding:** as of **EF Core 10** (released 2025-11-11 alongside .NET 10 LTS — [What's New in EF Core 10 — Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/what-is-new/ef-core-10.0/whatsnew)), the SQL Server EF Core provider ships **built-in, LINQ-based** vector search: `EF.Functions.VectorDistance(...)` (exact) and `.VectorSearch()`/`.WithApproximate()` (ANN), replacing the earlier community `EFCore.SqlServer.VectorSearch` plugin. [SQL Server Provider — Vector Search — EF Core | Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/providers/sql-server/vector-search) (`ms.date` 2026-06-09, updated 2026-07-13). Because these are ordinary LINQ queries over `context.Blogs`, **global query filters apply automatically** — meaning the idiomatic EF Core vector API on SQL Server enforces tenant isolation for free, and the "raw SQL bypasses isolation" lesson only shows up if you *deliberately* hand-write SQL instead.
- On PostgreSQL there's no Microsoft/Npgsql-official LINQ vector integration; the community package `Pgvector.EntityFrameworkCore` (pgvector org, not Npgsql/Microsoft) adds LINQ-queryable distance operators (`L2Distance`, `CosineDistance`, etc.) and `hnsw`/`ivfflat` index config on top of `Npgsql.EntityFrameworkCore.PostgreSQL`, current version **0.3.0** (needs EF Core 9/10; 0.2.2 for EF Core 8). [Pgvector.EntityFrameworkCore — NuGet](https://www.nuget.org/packages/Pgvector.EntityFrameworkCore/) / [pgvector-dotnet — GitHub](https://github.com/pgvector/pgvector-dotnet).

## Sharper mechanism: *why* the vector query specifically is non-composable

The general "composable `FromSqlRaw` gets filtered, unmapped `SqlQuery`/raw ADO.NET doesn't" rule leaves open a third case: `FromSqlRaw` **over a mapped entity type** that EF Core still can't compose. Composability requires the raw SQL to be wrappable as a subquery — official EF Core docs state it cannot contain `ORDER BY`, `TOP`/`LIMIT`, `OFFSET`, `DISTINCT`, `GROUP BY`, `HAVING`, or set operators. [SQL Queries — EF Core | Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/querying/sql-queries).

A vector similarity query is *structurally* one of these: it always needs `ORDER BY <distance> LIMIT k` (or `TOP k` on SQL Server) to be useful at all — you're not fetching all rows, you're fetching the nearest k. That means `context.Chunks.FromSqlRaw("SELECT ... ORDER BY embedding <=> @v LIMIT 5")` is **non-composable by construction**, so EF Core cannot wrap it with the tenant `WHERE` clause even though `Chunks` is a mapped `DbSet<ChunkEntity>` with a configured global filter. This isn't an edge case that might slip through review — it's the query shape every hand-written vector search will have, every time. Confirmed against the same composability rule for both SQL Server (`TOP`) and PostgreSQL (`LIMIT`).

**Consequence for the design:** the tenant predicate must be written into the raw SQL by hand (`WHERE "TenantId" = @tenantId` placed *before* the `ORDER BY`, so filtering happens before ranking, not after — filtering after ranking can return fewer than k rows or zero if the top-k-by-distance across all tenants happens to exclude the current tenant entirely) — never left to the global filter, because the global filter mechanically cannot reach this query.

## Practical implication

Because *both* ecosystems now offer a LINQ-friendly, filter-respecting path, "raw SQL is a deliberate design decision" has to be enforced procedurally, not assumed as a database limitation:

- Require every raw/hand-written vector query to take a `tenantId` parameter and assert it's present in the `WHERE` clause (code review rule, or a Roslyn/architecture test).
- The integration test proves the negative case: a raw query built *without* the tenant predicate must be shown to return cross-tenant rows, then the real query (with the predicate) must be shown not to. That's what makes the test a genuine argument, not a tautology.
- Consider native **Row-Level Security** (available on both SQL Server and Postgres, RLS on Postgres since 9.5) as a second, engine-level line of defense independent of application code — not required for the MVP, but worth naming in `DECISIONS.md` as a "when I'd reconsider" if the raw-SQL discipline alone ever felt insufficient.
