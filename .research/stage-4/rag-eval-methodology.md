# RAG eval methodology for Stage 4 (metrics, labels, judging, statistics, run logs)

Question: Stage 4 builds a 20–30 question eval set over 4 SEC filings (Apple 10-K/10-Q, JPMorgan 10-K/10-Q, two tenants) *before* any optimization, and a console harness `tools/Lumen.Eval` that calls the real `POST /api/search` and `POST /api/ask` with a JWT. Experiments E0–E7 compare vector-only vs hybrid, chunking 250/60 vs 400/100 vs 150/40 (re-upload changes chunk IDs), context topK, temperature, and the prompt/refusal behaviour, on a cheap mini-class Azure OpenAI answer model. What should the harness measure, how should the labels survive re-chunking, how should answers be scored, how big a difference is real at n≈25, and what should a run log look like? Is `Microsoft.Extensions.AI.Evaluation` worth using here, or should the scoring be hand-rolled?

Sources current as of 2026-10-01. Builds on `stage-2/chunking-testing-and-debugging.md` Finding 3 (RAGAS Context Precision/Recall, the OpenAI cookbook's Hit Rate/MRR, and Azure Foundry's process-vs-system evaluator split), which this file does not repeat.

## Recommendation

1. **Score deterministically wherever you can, and use an LLM judge only for prose answers.** Retrieval metrics, numeric answers, refusals and the cross-tenant trap all get hand-rolled code in `Lumen.Eval` and cost $0. Use an LLM judge (`EquivalenceEvaluator` from `Microsoft.Extensions.AI.Evaluation.Quality` 10.10.0) only for the "paraphrased prose" category. Pick a judge model that is stronger than the mini answer model and not the same one. The MEAI prompts are tuned against GPT-4o (Finding 1, Finding 4).
2. **Use MEAI.Evaluation as a library, not as a framework.** In a console app, call `evaluator.EvaluateAsync(...)` directly. The one optional extra is `DiskBasedReportingConfiguration`, which gives a free disk cache for judge calls and an `aieval report` HTML page. Your own JSONL run log stays the main record (Finding 1, Finding 7).
3. **Labels are "evidence anchors", never chunk IDs.** For each question, store the document by its stable title key, a human-readable section label, and 1–3 short, distinctive anchor strings taken from the source. A retrieved chunk counts as relevant when its *normalized* text contains every anchor in a group. Before each experiment (after every re-upload), run a lint pass over `GET /api/documents/{id}/chunks`. It checks that each anchor group still matches at least one chunk, and it flags anchors that match too many chunks. Keep anchors well under the smallest overlap (40 tokens for 150/40) so that a boundary is unlikely to cut them in half (Finding 2).
4. **Retrieval metrics: rank of first hit (raw), hit@1/3/5/10, and MRR@10.** For the 10-K vs 10-Q comparison questions, also report all-groups@k (both pieces of evidence present). Skip precision@k and nDCG: with 1–2 relevant items per question they either can't go above 1/k or add nothing beyond MRR. When comparing chunk configs, also log the number of retrieved tokens, because larger chunks make hit@k easier for free (Finding 3).
5. **Score answers by category.** Numbers: parse value + unit + sign, compare with a stated tolerance. Prose: judge equivalence (pass = ≥4 on the 1–5 scale). Unanswerable and cross-tenant: expected behaviour = refuse. Make refusal machine-detectable (a structured `answered: false` / fixed sentinel from `/api/ask`) instead of asking a judge. The cross-tenant trap has two parts. One is a **hard invariant**: no foreign document in the retrieval results, and if one appears the harness aborts. The other is a behaviour score: the model must refuse rather than answer JPMorgan facts from its own training data (Finding 4).
6. **Statistics at n=25.** One config's accuracy has a 95% CI of about ±18–20 pp, so never compare two configs by their headline numbers. Compare them *paired, per question*. For pass/fail metrics, use an exact McNemar test on the questions that flipped. A rough guide: about 6–0 or 8–1 net flips is the smallest result that reaches p<0.05. Swings of 1–3 questions are noise. For MRR, use a paired randomization test or a paired bootstrap. At temperature > 0, run each question 3–5× and score per-question averages (Finding 5).
7. **Protect the eval set.** Write questions and expected answers from the filings *before* looking at any system output, and freeze the file (record its SHA-256 in every run). Hold back ~5 questions, at least one per category, that no tuning decision is ever made on, and run them once at the end. Balance the categories at about 4–5 questions each, across both tenants and both filing types (Finding 6).
8. **Run log: one `run.json` (config snapshot) + one `results.jsonl` (one line per question per repeat)** under `tools/Lumen.Eval/runs/{timestamp}_{label}/`, plus a `compare` command that prints per-question flips and the McNemar p-value between two runs (Finding 7).

- **Default pass threshold** for the 1–5 Quality metrics is `MinimumPassingScore = 4.0`. Ratings map as >4 Exceptional, >3 Good, >2 Average, and so on, so a score below 4 is marked `failed` — [EvaluationMetricExtensions.cs](https://github.com/dotnet/extensions/blob/main/src/Libraries/Microsoft.Extensions.AI.Evaluation.Quality/EvaluationMetricExtensions.cs).
- **Judge model caveat, in the API docs themselves:** the prompt "is designed to be model-agnostic, [but] the performance … can vary depending on the model used, and can be especially poor when a smaller / local model is used". The prompt "has been tested against (and tuned to work well with)" **GPT-4o** — [EquivalenceEvaluator remarks](https://learn.microsoft.com/en-us/dotnet/api/microsoft.extensions.ai.evaluation.quality.equivalenceevaluator). In practice, judging with the same mini deployment that answers is the configuration the library warns against.
- **Use outside unit tests.** Every evaluator is a plain `IEvaluator` with `EvaluateAsync(messages, modelResponse, chatConfiguration, additionalContext)`, plus convenience overloads that take a `string` response ([API extension methods](https://learn.microsoft.com/en-us/dotnet/api/microsoft.extensions.ai.evaluation.quality.equivalenceevaluator)). The test framework appears only in the tutorial's `TestContext`-based scenario name: `CreateScenarioRunAsync(string scenarioName, …)` accepts any string, and the docs say "you can set it to any string" ([Learn: evaluate with reporting](https://learn.microsoft.com/en-us/dotnet/ai/evaluation/evaluate-with-reporting)). A console app can therefore use `DiskBasedReportingConfiguration.Create(storageRootPath, evaluators, chatConfiguration, enableResponseCaching: true, executionName)` unchanged. Set `executionName` per run (e.g. `E2-hybrid-2026-10-05T1030`), because "if you don't provide an execution name … results from one run are overwritten by the next" (same page).
- **Response caching.** The cache is `ResponseCachingChatClient : DistributedCachingChatClient` ([source](https://github.com/dotnet/extensions/blob/main/src/Libraries/Microsoft.Extensions.AI.Evaluation.Reporting/CSharp/ResponseCachingChatClient.cs)). Its key is a hash of (cache version, **messages, `ChatOptions`**, caching keys) — [DistributedCachingChatClient.GetCacheKey](https://github.com/dotnet/extensions/blob/main/src/Libraries/Microsoft.Extensions.AI/ChatCompletion/DistributedCachingChatClient.cs). Entries expire after **14 days** by default ([tutorial](https://learn.microsoft.com/en-us/dotnet/ai/evaluation/evaluate-with-reporting)). **Important for Lumen:** caching only covers calls made through the `ScenarioRun`'s `IChatClient`. Answer generation happens server-side inside `/api/ask`, so it is *not* cached by this; only the judge calls are. That is the behaviour we want: the system under test is re-run every time, and a judge call is reused only when question, ground truth and answer text are byte-identical. That also makes rerunning a run whose answers didn't change effectively free.
- **`dotnet aieval`** (package `Microsoft.Extensions.AI.Evaluation.Console`, install with `dotnet tool install --create-manifest-if-needed Microsoft.Extensions.AI.Evaluation.Console`) has three commands: `report` (`-p/--path`, `-o/--output`, `-n` last N executions, default 10, `-f html|json`, `--open`), `clean-results` and `clean-cache` — [Program.cs](https://github.com/dotnet/extensions/blob/main/src/Libraries/Microsoft.Extensions.AI.Evaluation.Console/Program.cs), [ReportCommand.Format.cs](https://github.com/dotnet/extensions/blob/main/src/Libraries/Microsoft.Extensions.AI.Evaluation.Console/Commands/ReportCommand.Format.cs). The report groups scenario names on `.`. If scenario names look like `{category}.{questionId}`, the HTML view aggregates per category for free ([tutorial](https://learn.microsoft.com/en-us/dotnet/ai/evaluation/evaluate-with-reporting)).
- **Custom metrics fit in.** Hit@k, numeric match and refusal can be written as `IEvaluator`s that return a `NumericMetric`/`BooleanMetric` without calling an LLM. The tutorial's `WordCountEvaluator` is exactly this pattern ([tutorial](https://learn.microsoft.com/en-us/dotnet/ai/evaluation/evaluate-with-reporting)), and it would put everything into one `aieval` report.

**Fit verdict.** Good fit as a *library* for the judge plus its cache. Optional and nice-to-have for the HTML report. A poor fit as the backbone of the harness. The core numbers (rank of first hit, numeric match, refusal, McNemar between runs) are about 200 lines of deterministic C#, and MEAI offers no retrieval metric that uses gold labels (its `RetrievalEvaluator` is itself an LLM judge that needs no ground truth). Hand-roll those parts and call `EquivalenceEvaluator` only for prose questions. `CompletenessEvaluator` is the alternative if the expected answers are multi-claim; RAGAS `FactualCorrectness`, which splits answers into claims and scores precision/recall/F1 ([docs](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/factual_correctness/)), does the same job but is Python, so it would need a sidecar and isn't worth one here. The NLP evaluators (BLEU/F1) are the wrong tool for the reason in Finding 4.

### 2. Labels that survive re-chunking

Chunk IDs (GUIDs) and `ChunkIndex` change with every re-upload and every chunk-size change. `DocumentId` changes on re-upload as well. Three label schemes have primary-source precedent:

- **Character spans in the source text (Chroma).** Chroma's chunking evaluation stores each relevant excerpt as `(corpus_id, start_index, end_index)` in the corpus text, found with `document.find(excerpt)`. A chunk counts by range intersection, so the labels are independent of how the text was chunked. IoU, token precision and token recall are computed over those ranges — [research page](https://www.trychroma.com/research/evaluating-chunking), [base_evaluation.py](https://github.com/brandonstarxel/chunking_evaluation/blob/main/chunking_evaluation/evaluation_framework/base_evaluation.py). **Why not as-is for Lumen:** our `CharStart`/`CharEnd` are documented as "approximate running offsets over overlapping chunks" (`stage-2/design.md` amendment, item 6), and `SearchResultDto` doesn't expose them. A span-based scheme would therefore need offset fixes in Stage 2 code before it could be trusted.
- **Answer/evidence string patterns (TREC QA lineage).** NIST automated TREC QA scoring with regular expressions that describe the gold answers, matched against system output by a script — e.g. [arXiv cs/0207058](https://arxiv.org/pdf/cs/0207058); the TREC-8 track itself was judged by humans reading "each string" ([Voorhees & Tice](http://www.lrec-conf.org/proceedings/lrec2000/pdf/26.pdf)). The OpenAI `evals` framework has the same idea built in as its `Includes` template ("ideal" string or list of strings that must appear in the output) — [build-eval.md](https://github.com/openai/evals/blob/main/docs/build-eval.md).
- **Reference contexts compared as strings (RAGAS `NonLLMContextRecall`).** This uses "non-LLM string comparison metrics to identify if a retrieved context is relevant", with explicit `reference_contexts` per question. The ID-based variant needs stable IDs, which we don't have — [RAGAS context recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/).

**Recommended scheme (project-local design, combining the above):**

```jsonc
{ "id": "AAPL-07", "tenant": "acme", "category": "table_value",
  "question": "...", "expected": { "kind": "number", "value": 416161, "unit": "USD_millions", "tolerancePct": 0.5 },
  "evidence": [ { "doc": "AAPL-10K-FY2025", "section": "Item 8 — Consolidated Statements of Operations",
                  "anchors": ["Total net sales", "416,161"] } ],
  "evidenceMode": "any" }        // "all" for 10-K vs 10-Q comparison questions (two groups, both needed)
```

- A chunk matches a group if it comes from the right document (looked up by title, resolved to the current `DocumentId` once per run) and its normalized text contains **all** of the group's anchors. Normalize by lowercasing, collapsing whitespace, folding Unicode quotes and dashes (`’`→`'`; the Stage 3 "Company’s best estimates" incident was exactly this kind of mismatch), and stripping the `|`/`$` table separators for numeric anchors, since Stage 2 tables can come out as `$ | 45,781`.
- **Keep anchors short** (a row label plus a value, or a 3–8-word phrase). With sliding-window overlap, a span shorter than the overlap usually lands whole in some chunk. The Stage 2 chunker is paragraph- and table-aware, though, not a pure sliding window, so this is likely rather than guaranteed. Hence the next point.
- **Label lint, run before every experiment (after re-upload):** fetch all chunks for the 4 filings and, for each anchor group, count matching chunks. **0 matches** means the label is broken under this chunking. Report it as "unlabelable" and keep it out of the hit@k denominator, rather than counting it as a retrieval miss, which would wrongly blame retrieval for a boundary artefact. **More than ~5 matches** means the anchor isn't distinctive (e.g. `"Total net sales"` alone), so add a second anchor. The lint costs $0 and turns "re-upload changes chunk IDs" from a blocker into a single check.
- Keep the `section` label for humans and for failure analysis by category (E1). It isn't used for scoring.
- Log the chunk IDs and `ChunkIndex` in the run log for debugging, but never match on them.

### 3. Retrieval metrics at 1–2 relevant items × 25 questions

Definitions:

- **hit@k (Hit Rate):** 1 if any relevant item is in the top k, else 0, averaged over questions — as used by the [OpenAI cookbook RAG eval](https://cookbook.openai.com/examples/evaluation/evaluate_rag_with_llamaindex).
- **recall@k:** relevant items in the top k / total relevant items. With a single relevant group it **equals hit@k**, so it only says something new for the two-group comparison questions. There, report the stricter **all-groups@k** (both the 10-K and the 10-Q evidence present).
- **MRR:** the mean over questions of 1/rank of the first correct item, and 0 if none appears in the cutoff. TREC-8 QA used a top-5 cutoff — [Voorhees & Tice, TREC-8 QA](http://www.lrec-conf.org/proceedings/lrec2000/pdf/26.pdf). Use MRR@10.
- **Precision@k / R-precision / MAP / nDCG:** standard definitions are in [Manning, Raghavan & Schütze, IR book §8.4](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html); nDCG(Q,k) = (1/|Q|) Σ Z_kj Σ_m (2^R(j,m) − 1)/log₂(1+m). With binary relevance and a single relevant item, nDCG@k = 1/log₂(1+rank). That ranks configs the same way MRR does (both are decreasing functions of the first-hit rank), so it adds nothing. Precision@k can't exceed 1/k (or 2/k), so it mostly reflects k. **Skip all four.**
- **Report the raw rank of the first hit per question** (or "miss"). At n=25 the per-question rank list *is* the analysis: the E1 failure review reads it directly, and the means are just summaries of it.
- **Chunk-size confound (E3):** at fixed topK, 400-token chunks hand the generator about 2.7× the text of 150-token chunks, so hit@k rises "for free". Chroma's token-level IoU/precision exists to penalize exactly this ([Chroma](https://www.trychroma.com/research/evaluating-chunking)). The cheap equivalent here: log `retrievedTokens` per question and compare chunk configs at an *equal context token budget* as well as at equal k.
- The IR book's warning carries over: variance across information needs (questions) is larger than variance across systems on the same need, so test collections must be "large and diverse enough to be representative" ([IR book §8.4](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html)). This is why the comparisons in Finding 5 are paired.

### 4. Answer scoring: numeric match, LLM judge, refusals, cross-tenant trap

- **Order of preference.** Anthropic's eval guidance: automate grading, prefer exact/string match for clear-cut answers, use LLM grading for nuanced criteria with detailed rubrics and reasoning before the score, and "use a different model to evaluate than the model used to generate the evaluated output" — [Anthropic: Create strong empirical evaluations](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests). OpenAI's guidance prefers "pairwise comparison or pass/fail for more reliability", adding reasoning before scoring, and validating the judge's agreement against your own human labels before optimizing for cost — [OpenAI evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices).
- **Numeric questions (table values, 10-K vs 10-Q deltas): deterministic.** Store `value`, `unit`/scale and `tolerancePct` in the expected answer. In the response, extract numbers, applying "billion/million" scale words and treating `(1,234)` as negative, the financial-table convention. Pass if any extracted number matches within tolerance (e.g. 0.5% so that "$416.2 billion" matches 416,161 million). If nothing can be parsed, mark the answer "unparsed" and send it to the judge, not straight to fail. Plain exact match is too brittle: in open-domain QA "more than 50% of lexical matching failures are attributed to semantically equivalent answers" ([Kamalloo et al. 2023, arXiv 2305.06984](https://arxiv.org/abs/2305.06984)). The same finding argues against BLEU/F1 for prose.
- **Prose questions: LLM judge, binary.** Use `EquivalenceEvaluator` (or `CompletenessEvaluator` for multi-claim answers) and collapse its 1–5 to pass/fail at the library's own threshold of ≥4 (Finding 1). Use a judge deployment **stronger than and different from** the mini answer model. Known judge biases are position, verbosity and self-enhancement (favouring answers from its own model family) — [Zheng et al. 2023, arXiv 2306.05685](https://arxiv.org/abs/2306.05685). That paper also reports strong judges reaching ">80% agreement" with humans, about human-to-human level. Verbosity bias matters here because a mini model padding its answer must not be rewarded. **Calibrate once:** after E0, grade the ~8–10 prose answers yourself, compare with the judge, and tighten the rubric where you disagree. The [OpenAI guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices) names "not calibrating your automated metrics against human evals" as an anti-pattern. Kamalloo et al. add that automated evaluators "struggle in detecting hallucinations" in long answers ([arXiv 2305.06984](https://arxiv.org/abs/2305.06984)), so a short expected answer and a short answer format make judging easier.
- **Cost (arithmetic, not a quoted price):** judge only the prose subset (~8 questions). Each judge prompt is roughly question + ground truth + answer + rubric, about 1–2k tokens, so a run is ~10–20k judge tokens, and reruns with unchanged answers hit the MEAI cache (Finding 1). Answer generation dominates the cost (25 × context topK × chunk tokens), and E3/E4 change it directly.
- **Unanswerable questions: score abstention as a behaviour.** SQuAD 2.0 introduced the requirement that systems "determine when no answer is supported by the paragraph and abstain from answering" ([Rajpurkar et al. 2018, arXiv 1806.03822](https://arxiv.org/abs/1806.03822)). Expected = `refuse`. To keep it deterministic, design `/api/ask` to return a structured signal (`answered: false`, or a fixed refusal sentence the prompt mandates) and match on that, not on a judge reading prose. Report two error rates separately, because E6 (prompt/refusal tuning) trades one against the other: **false-answer rate on unanswerables** (hallucination) and **false-refusal rate on answerables** (over-cautious).
- **Cross-tenant trap (e.g. logged in as the Apple tenant, asking for JPMorgan's net interest income):**
  1. **Hard invariant, not a metric:** if any retrieved chunk's `DocumentId` is not one of the tenant's own documents, the harness stops with an error. That would be an isolation bug, which Stage 3's tests already guard against.
  2. **Behaviour:** expected = `refuse`, scored like an unanswerable question. The real risk is *parametric knowledge*: a mini model has seen JPMorgan's and Apple's headline numbers in pre-training and can answer "correctly" with no retrieval behind it. Count such an answer as a **failure**, not a pass.
  3. The same logic gives a general diagnostic. Log the 2×2 of (retrieval hit?) × (answer correct?). "Correct answer + retrieval miss" means memorization or luck, not RAG, and it shows up on Apple's well-known figures too.

### 5. Statistics at n≈25: what difference is real

- **Single-config uncertainty.** The standard error of a proportion is √(p(1−p)/n). At n=25 the 95% half-width is about ±19.6 pp at p=0.5, ±18 pp at 0.7, and ±12 pp at 0.9 (computed). Anthropic's eval-statistics guidance says to report the SEM next to every score ([Anthropic: A statistical approach to model evaluations](https://www.anthropic.com/research/statistical-approach-to-model-evals); paper: [Miller 2024, "Adding Error Bars to Evals", arXiv 2411.00640](https://arxiv.org/abs/2411.00640)).
- **Compare configs paired, not as two independent percentages.** The same paper recommends paired-difference analysis because the same questions are hard or easy for both systems: "report pairwise information — mean differences, standard errors, confidence intervals, and correlations" ([Anthropic summary](https://www.anthropic.com/research/statistical-approach-to-model-evals)).
- **Pass/fail metrics (hit@5, answer correct): exact McNemar test.** It looks only at discordant questions: b = A pass/B fail, c = A fail/B pass. The exact version uses the binomial distribution on min(b, c) ([statsmodels `mcnemar`, `exact=True`](https://www.statsmodels.org/stable/generated/statsmodels.stats.contingency_tables.mcnemar.html)), and at this size there's no need for the chi-square approximation. Two-sided exact p-values (computed): 4–0 → 0.125, 5–0 → 0.063, **6–0 → 0.031**, 5–1 → 0.22, 7–1 → 0.070, **8–1 → 0.039**, 9–2 → 0.065. **Rule of thumb for this project:** a config change has to fix about 6 questions without breaking any, or about 8 while breaking 1, before calling it real. "+2 questions" is noise. Writing these thresholds down *before* E2 also gives DECISIONS.md an honest "the difference was / wasn't significant" line.
- **Continuous metrics (MRR, mean rank): paired randomization (permutation) test, or paired bootstrap.** Smucker, Allan & Carterette compared tests on TREC runs, recommended the randomization test, found "little practical difference between the randomization, bootstrap, and t tests", and advised against the sign and Wilcoxon tests ([CIKM '07, doi:10.1145/1321440.1321528](https://dl.acm.org/doi/10.1145/1321440.1321528)). Implementation: for 10,000 iterations, randomly swap A/B per question and count how often |mean diff| ≥ the observed one. That's about 15 lines of C#.
- **Repeated runs at temperature > 0 (E5).** Anthropic recommends "resampling answers from the same model several times, and using the question-level averages as the question scores" to cut within-question noise ([source](https://www.anthropic.com/research/statistical-approach-to-model-evals)). Practical form: 3 repeats per config (as in the kickoff plan), report the per-question pass rate (0, 1/3, 2/3, 1) and a **flip rate** (questions whose verdict isn't unanimous across repeats). The flip rate *is* E5's stability measure. Retrieval is deterministic for a given index (exact search), so repeats only matter for `/api/ask`.
- **Clustering.** Several questions about the same table or filing aren't independent. The paper notes clustered SEs "can be over three times as large as naive standard errors" ([source](https://www.anthropic.com/research/statistical-approach-to-model-evals)). With only 4 filings, don't try to estimate clustered SEs. Instead, spread questions across many different sections, and treat a gain that comes from a single table as weaker evidence.
- **Power:** n=25 can only detect large effects (≈20+ pp). Accept that, and use the per-question review (E1) for the smaller effects. If a decision ends up hinging on a 5–10 pp difference, the honest fix is more questions, which is what the paper's power-analysis recommendation implies ([arXiv 2411.00640](https://arxiv.org/abs/2411.00640)).

### 6. Eval-set design practice

- **Mix of typical, edge and adversarial cases**, built partly by domain experts — [OpenAI evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices). Include edge cases ([Anthropic](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)). For Lumen: 6 categories × ~4 = 24, plus a few extra in the categories you expect to be weakest (table values, exact terms). Split them across both tenants and both 10-K and 10-Q, so no category exists for one company only.
- **Write before you look.** Draft each question and expected answer from the filing itself, and have the user check it against the source (kickoff decision #2) *before* running anything against Lumen. Seeing system output first anchors the expected answer to what the system already does. Phrase prose questions in your own words rather than copying the filing's sentence: a question that repeats the chunk's wording measures lexical overlap, not semantic retrieval. The "exact term" category is the deliberate exception.
- **Validation vs test, in miniature.** "The more you use the same data to make decisions about hyperparameter settings … the less confidence" you can have on new data, and evaluation sets "'wear out' with repeated use" ([Google ML Crash Course: Dividing the original dataset](https://developers.google.com/machine-learning/crash-course/overfitting/dividing-datasets)). Over E0–E7 we will tune 5+ knobs on the same 25 questions, which is real overfitting pressure. **Hold out ~5 questions** (one per category, marked `"split": "holdout"`). The harness skips them by default, and they run once on the final config, as a reported number in DECISIONS.md.
- **Freeze and version.** Record the eval file's SHA-256 in every run. If a question or expected answer has to be fixed (an error found in the reference), bump the version, re-score the old runs' saved answers against the new key if possible, and note that the earlier comparisons predate the fix. The [OpenAI guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices) recommends growing the eval set over time, and that works best as versioned additions, not silent edits.

### 7. Run-log format

Precedent: OpenAI `evals` stores samples as JSONL ("a unique JSON object per line", with `input` and `ideal` keys) and records run events "into local JSONL logs which can be inspected using a text editor or analyzed programmatically" ([build-eval.md](https://github.com/openai/evals/blob/main/docs/build-eval.md), [run-evals.md](https://github.com/openai/evals/blob/main/docs/run-evals.md)). MEAI's result store keeps per-execution JSON on disk under `storageRootPath` ([tutorial](https://learn.microsoft.com/en-us/dotnet/ai/evaluation/evaluate-with-reporting)).

Recommended layout: `tools/Lumen.Eval/runs/{yyyyMMddTHHmmss}_{label}/`

- **`run.json`, the config snapshot** (one object): `label`, `startedAt`, `gitCommit` + `gitDirty`, `evalSetSha256` + version, `split` (dev/holdout), `apiBaseUrl`. Retrieval settings: `mode` vector|hybrid, hybrid weights / RRF k, `searchTopK`, `contextTopK`, `contextTokenBudget`. Chunking: `maxTokens`, `overlap` (read back from the server, not assumed), `chunkCountPerDoc`. Models: embedding model/deployment, chat deployment, `temperature`, `topP`, `maxOutputTokens`, `promptVersion` + prompt SHA, judge deployment, MEAI package version. Plus `repeats` and the label-lint summary (unlabelable question IDs).
- **`results.jsonl`**, one line per (question, repeat): `id`, `repeat`, `category`, `tenant`, `question`. Retrieved items `[{rank, docTitle, chunkIndex, chunkId, chunkType, tokenCount, distance, matchedGroups}]`, `retrievedTokens`, `firstHitRank` (null = miss), `hitAt{1,3,5,10}`, `allGroupsAt5`, `rr`. Answer side: `answerText`, `citations`, `answered` (structured refusal flag), `scoreKind` (number|judge|refusal), `numericParsed`, `numericPass`, `judgeScore`, `judgeReason`, `pass`. Plus `latencyMsSearch`, `latencyMsAsk`, `tokensIn`, `tokensOut`, `error`.
- **`summary.json`**: aggregates per category and overall, with SEM.
- A **`compare <runA> <runB>`** command prints the per-question flip table, b/c counts, the exact McNemar p for hit@5 and answer pass, and the paired randomization p for MRR. Most of what the user sees after an experiment should come from this command.
- The console output (kickoff decision #3) is a rendering of these files, so nothing is lost when the terminal scrolls.

## Uncertain / could not verify

- **The McNemar "6–0 / 8–1" thresholds** are my own calculation from the exact binomial formula that statsmodels documents. They are not quoted from a source, and they assume two-sided α=0.05 with no correction for running many experiments (E0–E7 compare many pairs, so multiple comparisons make false wins more likely than 5%).
- **Anchor-survives-boundary** is reasoning about sliding-window overlap, not a published guarantee. Lumen's chunker is paragraph/table-aware, so the lint step (Finding 2) is what actually verifies it per config.
- **MEAI judge quality with non-GPT-4o judges** (e.g. a newer `gpt-4.1`/`gpt-5`-class deployment, or a mini model) isn't documented beyond "can be especially poor when a smaller / local model is used". Which deployment the Azure resource offers, and its price, wasn't checked. The kickoff's `top_k`/reasoning-model `temperature` questions belong to a separate research file.
- **The OpenAI best-practices page** names a specific judge model ("Start with gpt-6-astra…") in the fetched copy. I couldn't confirm that model name from a second source, so I cited the page only for model-independent advice.
- **Whether `ChatOptions.Temperature` changes affect MEAI judge cache hits** follows from `GetCacheKey` hashing `options`. That is read from source, not tested. Judge options are normally fixed, so this shouldn't matter in practice.
- **Chroma's span-based IoU** could become usable if Stage 2's `CharStart`/`CharEnd` were made exact and exposed in `SearchResultDto`. That's a code change, out of scope here, and not needed given the anchor scheme.
